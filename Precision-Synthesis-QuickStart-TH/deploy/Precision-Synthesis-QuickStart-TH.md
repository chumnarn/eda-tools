# คู่มือ Siemens Precision Synthesis Quick Start (ฉบับเต็ม, ภาษาไทย)

เอกสารประกอบการอบรม **Siemens Precision Synthesis (PS)** สำหรับวิศวกรและนักศึกษาสายอิเล็กทรอนิกส์
โดยยึดลำดับงานจาก **Precision Synthesis Quick Start Guide รุ่น PS2018.1** และขยายเป็นแบบฝึกหัด (Lab)
บนบอร์ด **Digilent Nexys A7-100T** ตั้งแต่สร้าง RTL จนได้ bitstream

> คู่มือฉบับนี้เขียนสำหรับ **การอบรมในห้องเรียน** ทุกบทมีแบบฝึกหัดที่ทำต่อเนื่องกันได้
> โดยใช้ RTL ชุดเดียวกันตลอดคู่มือ ผู้เรียนจึงเห็นวงจรจริงตั้งแต่โค้ดจนถึงชิป

## 1. กลุ่มผู้อ่านและสิ่งที่ต้องรู้มาก่อน

| กลุ่ม | ต้องมีพื้นฐาน |
|---|---|
| นักศึกษาปี 3–4 สาย EE/CE | ดิจิทัลและตรรกะ, Verilog ระดับพื้นฐาน, พื้นฐาน MOSFET |
| นักศึกษาปี 5–7 / ผู้สนใจทำดีไซน์ชิป | ผ่านบทที่ 1–2 มาก่อน หรือเคยทำโปรเจกต์ FPGA มาแล้ว |
| ผู้สอน / ผู้ช่วยสอน | ใช้เป็นลำดับหัวข้อและ checklist การจัดปฏิบัติการ |

**เครื่องมือที่ต้องใช้**

| ขั้นตอน | เครื่องมือ | หมายเหตุ |
|---|---|---|
| เขียน/ตรวจ RTL | Precision Synthesis (Siemens EDA) | เป็นเครื่องมือหลักของคู่มือนี้ |
| จำลอง RTL | QuestaSim หรือ ModelSim (Siemens) | ต้องใช้ VHDL-2008 |
| จำลองแบบเสริม | GHDL (โอเพนซอร์ส) | ใช้ตรวจ testbench ได้ฟรี ดูบทที่ 1 |
| วางวาง/เดินสาย/สร้าง bitstream | AMD Vivado (เวอร์ชันที่รองรับ Artix-7) | ใช้รับเน็ตลิสต์ EDIF จาก Precision |
| โปรแกรมลงบอร์ด | Vivado Hardware Manager / openFPGALoader | ทดสอบบนฮาร์ดแวร์จริง |

> **หมายเหตุเรื่องตัวเลขในคู่มือ**
> ตัวเลขผลลัพธ์ของเครื่องมือในคู่มือเป็น **ตัวอย่างประกอบการอธิบาย** ไม่ใช่ผลจากการรันจริง
> เพราะตัวเลขขึ้นกับรุ่นของซอฟต์แวร์ ค่าคอนฟิก และเวอร์ชันไลบรารี
> ผู้เรียนต้องรันเองแล้วเทียบกับผลของตัวเองในตารางบันทึกผล (labs/results/)
> คำสั่งที่ขึ้นกับรุ่นจะกำกับไว้ด้วยคำว่า *(ตรวจสอบกับเอกสารของรุ่นที่ใช้)*

### ข้อตกลงเรื่อง "ตัวเลขในคู่มือ"

ตัวเลขผลลัพธ์ของเครื่องมือในคู่มือเป็น **ตัวอย่างประกอบการอธิบาย** ไม่ใช่ผลจากการรันจริง
เพราะตัวเลขขึ้นกับรุ่นของซอฟต์แวร์และค่าคอนฟิก ผู้เรียนต้องรันเองแล้วเทียบกับตัวเอง
คำสั่งที่ขึ้นกับรุ่นจะกำกับไว้ด้วยว่า *(ตรวจสอบกับเอกสารของรุ่นที่ใช้)*

## 6. สิ่งที่ควรรู้ก่อนเริ่ม

1. **Precision เป็นเครื่องมือที่ต้องมีใบอนุญาต** หากโรงเรียนไม่มีสิทธิ์ใช้
   ให้ทำแล็บในบทที่ 1 และอ่านบทที่ 2–5 ในเชิง "ทำตามแล้วนำผลมาเทียบกัน"
   โดยใช้ตัวอย่างรายงานที่แนบไว้ในบท แล้วทำต่อใน Vivado จริง
2. **ชื่อเมนูและคำสั่งเปลี่ยนตามรุ่น** เอกสารอ้างอิง PS2018.1
   หากใช้รุ่นอื่นให้เทียบเมนูกับ Command Reference ของรุ่นนั้น
3. **สิ่งที่ไม่ควรทำ** อย่าเริ่มจากการกด Synthesize ทันทีที่ยังไม่ได้ตรวจ RTL
   และอย่าเชื่อตัวเลขเวลาจากขั้นสังเคราะห์ว่าเป็นคำตัด เพราะค่านี้ยังไม่รวมความหน่วงการเดินสาย

# บทที่ 0 — ภาพรวมของ Precision Synthesis และเตรียมสภาพแวดล้อม

## 0.1 Precision Synthesis คืออะไร

**Siemens Precision Synthesis (PS)** คือเครื่องมือสังเคราะห์ตรรกะระดับอุตสาหกรรมที่ทำงานในสองบทบาทเดียวกัน

1. **ตัวสังเคราะห์ RTL (RTL Synthesis)** — รับ RTL (VHDL/Verilog) แล้วแปลงเป็นเน็ตลิสต์
   พร้อมประเมินเวลาและพื้นที่โดยใช้ไลบรารีเซลล์จริงของอุปกรณ์เป้าหมาย
2. **ตัวเชื่อมโยงระหว่างเครื่องมือ (Cross-tool Platform)** — เป็นฐานข้อมูลกลางของทั้งระบบ
   ทำให้มองเห็นแบบเรียบง่ายของทั้ง RTL และเน็ตลิสต์ในที่เดียว และย้อนกลับไปหาโค้ดต้นทางได้

ความสามารถที่โดดเด่นของ PS ที่เกี่ยวข้องกับคู่มือนี้

| ความสามารถ | ความหมายในทางปฏิบัติ |
|---|---|
| ฐานข้อมูลกลางของ RTL และการสังเคราะห์ | เปิด schematic ของเน็ตลิสต์แล้วเจาะลงไปที่โค้ด HDL ต้นทางได้ในจุดเดียว ไม่ต้องเดาเองว่าเซลล์ไหนมาจากโค้ดไหน |
| การวิเคราะห์เวลาในตัว | ดู setup/hold slack ของเส้นทางวิกฤตได้ทันทีหลังสังเคราะห์ โดยไม่ต้องรอ Vivado |
| การแยกส่วนที่วิกฤต | เก็บส่วนที่เสียเวลามากที่สุดไว้แยก แล้วปรับปรุงเฉพาะจุดนั้น โดยไม่กระทบส่วนอื่น |
| การปรับปรุงอัตโนมัติ | เรียกอัลกอริทึมปรับปรุงขั้นสูงได้โดยไม่ต้องเขียนสคริปต์เอง |

### จุดยืนของ PS เมื่อเทียบกับ Vivado

PS ไม่ได้แทนที่ Vivado สำหรับงาน FPGA แต่ทำงาน **ก่อนหน้า** Vivado ในลำดับดังนี้

```text
RTL (VHDL/Verilog)
      │
      ▼
┌─────────────────────────┐
│  Precision Synthesis    │  ตั้งเป้าหมายเวลา, เลือก part, สังเคราะห์,
│  (PS2018.1)             │  วิเคราะห์ QoR, ส่งต่อเน็ตลิสต์ EDIF
└─────────────────────────┘
      │  EDIF + XDC/Tcl
      ▼
┌─────────────────────────┐
│  AMD Vivado             │  วางวาง (place), ปรับแต่ง (phys_opt),
│                         │  เดินสาย (route), ตรวจ DRC, สร้าง bitstream
└─────────────────────────┘
      │
      ▼
   bitstream → บอร์ด Nexys A7-100T
```

**ข้อควรเข้าใจสำคัญ**: ตัวเลขเวลาที่ PS รายงานหลังสังเคราะห์ **ยังไม่ใช่คำตัด**
เพราะยังไม่มีข้อมูลการวางวางและการเดินสายจริง คำตัดของงาน FPGA มาจาก Vivado หลัง route เสร็จ
บทที่ 5 ของคู่มือนี้จะให้เห็นผลของความต่างนี้อย่างชัดเจน

## 0.2 ภาพรวมลำดับงานตาม PS2018.1

คู่มือต้นฉบับแบ่งงานเป็น 3 ขั้นตอน ดังนี้

### ขั้นที่ 1 — Set-Up Precision

| ขั้น | รายละเอียดจากคู่มือต้นฉบับ | ผลลัพธ์ที่ต้องการ |
|---|---|---|
| 1a | Create project | โปรเจกต์ที่มีชื่อและโฟลเดอร์ชัดเจน |
| 1b | Add design source files — อ่านได้ทั้ง **VHDL, Verilog, EDIF, SDC** | รู้จักไฟล์ต้นทางทั้งหมดและไฟล์เงื่อนไขเวลา |
| 1c | Select device | ไลบรารีเซลล์และค่า delay ตรงกับชิปจริง |
| 1d | Set Frequency | ทุกเส้นทางที่สนใจมีนาฬิกากำกับ ไม่มีเส้นทางค้างไม่ถูกจำกัด |

### ขั้นที่ 2 — Run Synthesis

| ขั้น | รายละเอียดจากคู่มือต้นฉบับ | ผลลัพธ์ที่ต้องการ |
|---|---|---|
| 2a | Compile | อ่าน RTL สำเร็จ รู้จักโมดูลระดับบนสุด ไม่มี error |
| 2b | Synthesize | ได้เน็ตลิสต์ + รายงานเวลา/พื้นที่ |

### ขั้นที่ 3 — Analyze and Place & Route

| ขั้น | รายละเอียดจากคู่มือต้นฉบับ | ผลลัพธ์ที่ต้องการ |
|---|---|---|
| 3a | Report timing / View critical path schematics / Trace components from schematics to HDL sources | เข้าใจว่าเส้นทางวิกฤตเกิดจากโค้ดส่วนไหน และแก้ได้ |
| 3b | Run integrated Place and Route in Precision and review reports | รายงานการวางวาง/เดินสาย (สำหรับ ASIC) และรายงานของเครื่องมือปลายทาง |

> **หมายเหตุสำคัญเรื่อง 3b**: Precision มี Place & Route แบบผสมผสานสำหรับ **ASIC**
> แต่สำหรับ **FPGA ของ Xilinx** เส้นทางมาตรฐานคือส่งต่อเป็น EDIF ไปยัง Vivado
> คู่มือนี้จึงทำหั้งสองทาง: บทที่ 4 อธิบายทั้งทาง ASIC (เชิงหลักการ)
> และทาง FPGA ที่ใช้จริงในแล็บ

## 1.1 หลักการเขียน RTL ที่ Precision Synthesis รองรับ

### 1.1.1 มาตรฐานภาษา

Precision Synthesis รองรับ VHDL-93, VHDL-2002 และ VHDL-2008
และใช้แพ็กเกจมาตรฐาน `ieee.std_logic_1164` กับ `ieee.numeric_std`

| ข้อควรระวัง | รายละเอียด |
|---|---|
| ระบุมาตรฐานในไฟล์ | เพิ่ม `library ieee;` และ `use ieee.std_logic_1164.all;` `use ieee.numeric_std.all;` |
| ไม่ใช้ `std_logic_arith` | แพ็กเกจนี้เป็นของ Synopsafe และมีพฤติกรรมกับ signed/unsigned กำกวม ให้ใช้ `numeric_std` แทน |
| ตั้งชื่อไฟล์ให้สื่อความหมาย | เช่น `alu8.vhd`, `top_alu8.vhd` |

### 1.1.2 สิ่งที่ทำได้และไม่ควรทำ

| ทำได้ | ไม่ควรทำ (สังเคราะห์ไม่ผ่านหรือผลลัพธ์เพี้ยน) |
|---|---|
| `process (all)` พร้อมกำหนดค่าเริ่มต้นให้ครบทุกเอาต์พุต | ใช้ `wait`/`after` ในโค้ดที่สังเคราะห์ |
| ฟังก์ชันคงที่ที่คำนวณค่าตอนเอลาโบเรต เช่น `clog2` | ใช้ตัวแปรที่ไม่ใช่ค่าคงที่เป็นความยาวบิต |
| `numeric_std` เต็มรูปแบบ | ใช้ `'+'` ระหว่าง `signed` กับ `integer` โดยไม่แปลงชนิด |
| `generate` และ `for generate` | ใช้ `real`, `time` ในตรรกะเชิงวิเคราะห์ |
| `shared variable` ไม่แนะนำ | ใช้ shared variable (PS รองรับบางกรณีแต่ตรวจสอบยาก) |

### 1.1.3 กฎข้อที่ 1 — ไม่ให้เกิด latch

ใน VHDL ถ้า signal ถูก assign ใน process แล้วไม่ได้ assign ทุก branch จะกลายเป็น latch
ซึ่ง Precision จะสังเคราะห์ออกมาได้ แต่ผลลัพธ์ที่ได้มักไม่ตรงกับความคาดหมาย

```vhdl
-- ผิด: ไม่ได้กำหนดค่าให้ y ในทุกกรณี
process (op)
begin
  if op = "000" then
    y <= a + b;
  end if;
end process;

-- ถูก: กำหนดค่าเริ่มต้นก่อน แล้วค่อยแก้เฉพาะกรณีที่ต้องการ
process (all)
  variable y_v : signed(W-1 downto 0);
begin
  y_v := (others => '0');
  case op is
    when "000" => y_v := a + b;
    when "001" => y_v := a - b;
    when others => y_v := (others => '0');
  end case;
  y <= y_v;
end process;
```

> ในโค้ดของคู่มือนี้ใช้รูปแบบที่สองทั้งหมด เพื่อให้ผลของการสังเคราะห์ตรงกับผลของการจำลองเสมอ

### 1.1.4 กฎข้อที่ 2 — process ที่ไวต่อนาฬิกาต้องมี `rising_edge(clk)` เสมอ

นี่คือบั๊กที่พบจริงระหว่างทำแล็บนี้ และเป็นบั๊กที่ทำให้ผลจำลองกับผลสังเคราะห์
**คนละกันอย่างเงียบ ๆ** ซึ่งเป็นอันตรายที่สุด

```vhdl
-- ผิด: process จะทำงานทั้งขอบขึ้นและขอบลง
--       ตัวชี้จึงเดินสองครั้งต่อหนึ่งรอบนาฬิกา
process (clk, rst_n)
begin
  if rst_n = '0' then
    cnt <= (others => '0');
  else
    cnt <= cnt + 1;
  end if;
end process;

-- ถูก
process (clk, rst_n)
begin
  if rst_n = '0' then
    cnt <= (others => '0');
  elsif rising_edge(clk) then
    cnt <= cnt + 1;
  end if;
end process;
```

**อาการที่พบ**: FIFO ขนาด 8 ช่อง "เต็ม" หลังเขียนเพียง 4 ค่า
และตัวสะสม INT8 MAC ให้ผลเป็น **สองเท่า** ของที่ถูกต้อง
การจำลองด้วย testbench ที่ไม่ตรวจกรณีนี้จะผ่านทั้งที่การทดสอบบนฮาร์ดแวร์จะพัง

> ให้เพิ่มการตรวจ "นับรอบนาฬิกาจริง" ลงใน testbench เสมอ เช่น ตรวจว่าตัวนับเพิ่มขึ้น 1 ในทุกรอบ

### 1.1.5 กฎข้อที่ 3 — ระวังเรื่องการต่อสัญญาณ

ใน VHDL การต่อสัญญาณ `A & B` หมายถึง **A อยู่บิตสูงกว่า** B
ซึ่งตรงข้ามกับความเข้าใจทั่วไปของคนที่มาจาก Verilog

```vhdl
-- ต้องการให้ SW[7:0] = a และ SW[15:8] = b
-- ต้องเขียน b ก่อนแล้วค่อย a
sw <= std_logic_vector(byte_of(b) & byte_of(a));
```

บั๊กนี้ทำให้ผลบวกถูก (เพราะสลับตัวก็ได้ผลเท่ากัน) แต่ผลลบผิด
ทำให้ testbench ที่ทดสอบเฉพาะคำสั่ง ADD จะผ่านทั้งที่โค้ดผิด

> **เคสในคู่มือนี้**: `tb_top_alu8.vhd` ใช้การทดสอบทุกคำสั่ง จึงจับบั๊กนี้ได้
> สอนให้ผู้เรียนใช้ **ตารางคำสั่งที่ครอบคลุมทุกโหมด** ไม่ใช่แค่โหมดเดียว

## 1.2 โมดูล RTL ที่ใช้ตลอดคู่มือ

| ไฟล์ | หน้าที่ | ใช้สอนเรื่อง |
|---|---|---|
| `rtl/alu8.vhd` | หน่วยคำนวณ 8 บิตแบบมีเครื่องหมาย มีแฟล็ก zero/overflow | การเขียน combinational logic, การขยายสัญญาณ, การตรวจ overflow |
| `rtl/hex2seg.vhd` | ถอดเลขฐาน 16 เป็นรูปแบบจอ 7 ส่วน | ตารางความจริงแบบ lookup |
| `rtl/sync_fifo.vhd` | FIFO แบบตรง 8 ช่อง × 32 บิต ตัวชี้แบบ Gray code | ตัวชี้ Gray code, backpressure, การสังเคราะห์เป็น FF/LUTRAM |
| `rtl/int8_mac.vhd` | หน่วยคูณสะสม INT8 แบบไปป์ไลน์ 2 ขั้น | ไปป์ไลน์, AXI-Stream handshake, การสังเคราะห์เป็น DSP48 |
| `rtl/top_alu8.vhd` | โมดูลบนสุดสำหรับบอร์ด Nexys A7-100T | เส้นทางเวลา I/O → register → I/O, รีเซ็ต, แบ่งภาพจอ |

### 1.2.1 จุดที่ต้องสังเกตใน `alu8.vhd`

**(1) ความกว้างของค่าเลื่อน**

```vhdl
constant SHW : positive := clog2(W);
sh_u := unsigned(b(SHW-1 downto 0));
sh_n := to_integer(sh_u);
```

ต้อง mask ค่าเลื่อนให้เหลือเท่าจำนวนบิตที่ใช้เลื่อนจริง
ถ้าไม่ mask แล้วเลื่อนเกินความกว้างข้อมูล ผลจะเป็นศูนย์ทั้งหมด
(นี่คือบั๊กจริงที่เคยพบในเวอร์ชัน Verilogของคู่มือ ASIC ก่อนหน้านี้)

**(2) การขยายสัญญาณแบบมีเครื่องหมาย**

```vhdl
a_ext := resize(a, W+1);
b_ext := resize(b, W+1);
...
if s_v(W) /= s_v(W-1) then
  ov_v := '1';
end if;
```

ใช้ `resize()` เสมอ อย่าต่อบิตด้วยมือ เพราะการต่อบิตด้วยมือจะผิดเมื่อค่าเป็นลบ

**(3) การเลื่อนขวาเชิงอารีเมติก**

`shift_right` ของ `numeric_std` ทำการเลื่อนระดับบิต จึงเท่ากับการหารแบบตัดเศษลง (floor)
ต่างจากการหารของเลขจำนวนเต็มใน VHDL ที่ตัดเศษเข้าหาศูนย์
แบบจำลองอ้างอิงใน testbench จึงต้องมีฟังก์ชัน `fdiv` พิเศษ

### 1.2.2 จุดที่ต้องสังเกตใน `top_alu8.vhd`

โมดูลบนสุดนี้สร้าง **เส้นทางเวลา 2 เส้น** ที่จะเห็นในรายงานของ Precision และ Vivado

```text
 SW[15:0] / BTN[2:0]  ──►  [ ALU แบบ combinational ]  ──►  รีจิสเตอร์  ──►  LED / จอ 7 ส่วน
   (อินพุต)                    (ตรรกะ)                  (FF)          (เอาต์พุต)
        └── set_input_delay ──────────┘                    └── set_output_delay ──┘
```

การลงทะเบียนผลลัพธ์มีผลสำคัญสองข้อ

1. LED ไม่กะพริบเมื่อผู้ใช้โยกสวิตช์ (ค่าคงที่ในวงจรจริง)
2. มีเส้นทางรีจิสเตอร์ → เอาต์พุต ที่ต้องถูกจำกัดเวลาและตรวจ hold หลัง routing

รีเซ็ตเป็นแบบ **synchronous** (`if CPU_RESETN = '0'` ภายใน `rising_edge`)
จึงมีเส้นทางจากรีเซ็ตไปยังจุดตั้งค่าเริ่มต้นของรีจิสเตอร์
ต้องตัดออกจากการวิเคราะห์เวลาด้วย `set_false_path` ใน SDC/XDC

## 1.3 testbench แบบตรวจตัวเอง (self-checking testbench)

### 1.3.1 หลักการ 5 ข้อ

1. **ตรวจตัวเองได้** — testbench ต้องตัดสินใจเองว่าผ่านหรือไม่ผ่าน และรายงานผล
2. **ใช้แบบจำลองอ้างอิงคนละวิธี** — ถ้าใช้ตรรกะเดียวกับ RTL บั๊กทั้งสองฝั่งจะหายไปพร้อมกัน
3. **นับจำนวนข้อผิดพลาด** — ไม่ใช่ "หยุดที่ข้อผิดพลาดแรก" เพราะจะได้ข้อมูลแค่จุดเดียว
4. **ปิดท้ายด้วยผลลัพธ์ชัดเจน** — `PASS` พร้อมจำนวนเคส หรือ `FAIL` พร้อมรายละเอียด
5. **กระตุ้นแบบครอบคลุม** — ทดสอบทุกโหมดของตัวออกแบบ ไม่ใช่แค่เส้นทางหลัก

### 1.3.2 แบบจำลองอ้างอิงที่ "คนละวิธี"

ในคู่มือนี้ RTL ใช้ `numeric_std` บนสัญญาณแบบ signed
แต่แบบจำลองอ้างอิงใน `tb/alu_ref_pkg.vhd` ใช้ **เลขจำนวนเต็ม (integer)** ซึ่งเป็น arithmetic อิสระจาก RTL

```vhdl
-- ในแพ็กเกจอ้างอิง
procedure ref_alu(a_i, b_i : integer; op_i : std_logic_vector(2 downto 0);
                   y_o : out std_logic_vector(7 downto 0);
                   ovf_o : out std_logic; zero_o : out std_logic);

-- แบบจำลองการบวก: คำนวณก่อนตัดที่ 8 บิต จึงเห็น overflow ได้
when "000" =>
  full := a_i + b_i;
  if (full > 127) or (full < -128) then
    ovf_o := '1';
  end if;
  y_o := byte_of(full);
```

ข้อดีของการคำนวณก่อนตัด: เมื่อผลลัพธ์เต็ม 8 บิตทั้งที่ยังไม่เกินช่วง
ค่าจริงยังถูกต้อง แต่เมื่อเกินช่วงจะเห็นได้ทันที

### 1.3.3 ข้อจำกัดของภาษา VHDL ที่พบจริง

**ข้อควรรู้ 1 — อักษรไทยใช้ใน string literal ไม่ได้**

```vhdl
-- ผิด: GHDL และ ModelSim จะรายงานว่า
--       "invalid character not allowed, even in a string"
report "ผิดพลาด: a=" & integer'image(a_v);

-- ถูก: ใช้ภาษาอังกฤษในข้อความ แล้วใส่คำอธิบายไทยไว้ใน comment
report "MISMATCH y: a=" & integer'image(a_v);
```

คำอธิบายภาษาไทยใน **comment** ไม่มีปัญหา เพราะ comment ไม่ได้อยู่ในข้อกำหนดของภาษา

**ข้อควรรู้ 2 — `others` ใช้ใน expression ไม่ได้**

```vhdl
-- ผิด: "others' choice not allowed for an aggregate in this context"
if y_v = (others => '0') then

-- ถูก: ใช้ constant
constant ZERO_VAL : signed(W-1 downto 0) := (others => '0');
if y_v = ZERO_VAL then
```

**ข้อควรรู้ 3 — การสุ่มต้องทำซ้ำได้**

ใช้ LFSR (linear feedback shift register) แทนฟังก์ชันสุ่มของระบบ
เพื่อให้ผลการทดสอบเหมือนเดิมทุกครั้ง และเก็บ seed ไว้ในรายงาน

### Lab 1.1 — สร้าง testbench แบบตรวจตัวเองสำหรับ alu8

**เป้าหมาย**: เรียนรู้การเขียน testbench ที่ตรวจตัวเองและรายงานผล

### Lab 1.2 — ตรวจจับบั๊ก `rising_edge`

**คำถาม**: ถ้าไม่มี testbench คุณจะพบบั๊กนี้ได้อย่างไร และค่าในรายงานของ Precision

### Lab 1.3 — เพิ่มการทดสอบของคุณเอง

**เป้าหมาย**: ฝึกเขียนกรณีทดสอบเพิ่มเติม

## 2.2 ขั้นที่ 1b — Add design source files

### 2.2.1 ชนิดไฟล์ที่ PS อ่านได้

ตามคู่มือ PS2018.1 Precision อ่านไฟล์ได้ 4 ชนิด

| ชนิด | หน้าที่ | ในแล็บนี้ใช้ไฟล์ใด |
|---|---|---|
| **VHDL** | โค้ดออกแบบ | `rtl/alu8.vhd`, `rtl/hex2seg.vhd`, `rtl/top_alu8.vhd` |

| **SDC** | เงื่อนไขเวลา (ขั้นที่ 1d) | `sdc/top_alu8.sdc` |

> ในทางปฏิบัติโปรเจกต์ขนาดใหญ่จะมีทั้ง 4 ชนิดอยู่ด้วยกัน
> เช่น โมดูลหลักเป็น VHDL, IP core จากผู้ขายเป็น EDIF, และมี SDC รวม

### 2.2.2 เพิ่มไฟล์ใน GUI

```text
File > Add Files...
  [Add Files...] เลือกชนิดไฟล์ VHDL
  เลือก: alu8.vhd, hex2seg.vhd, top_alu8.vhd
  [OK]
```

**ลำดับการเพิ่มไฟล์สำคัญ**: PS ต้องเห็นโมดูลที่เป็น dependency ก่อน
จึงเพิ่ม `alu8.vhd` → `hex2seg.vhd` → `top_alu8.vhd` (leaf ก่อน top)

หลังเพิ่มแล้วให้ตรวจว่า PS รู้จัก hierarchy ถูกต้อง

```text
Design > Show Hierarchy
  ต้องเห็น:
    top_alu8
     ├── alu8
     └── hex2seg  (x2)
```

ถ้า hierarchy ไม่ถูกต้อง แสดงว่า:
- เพิ่มไฟล์มาผิดลำดับ → ลบแล้วเพิ่มใหม่
- ชื่อ entity ไม่ตรงกับชื่อที่ instantiate
- มีไฟล์ค้างอยู่ในโปรเจกต์ → ตรวจรายการไฟล์ทั้งหมด

### 2.2.3 ข้อควรระวังเรื่องไลบรารี

2. **ส่งต่อเป็นเน็ตลิสต์ VHDL/Verilog แทน EDIF** แล้วให้ Vivado สังเคราะห์ต่อ
   (เสียข้อดีของการใช้ไลบรารีของอุปกรณ์ใน PS แต่ยังได้ผลลัพธ์บนฮาร์ดแวร์)
3. **อัปเกรดรุ่นของ PS** แล้วทำตามขั้นตอนเดิมทั้งหมด

| `create_clock` | สร้างนาฬิกาหลัก 100 MHz (คาบเวลา 10 ns) | **ไม่มีเส้นทางไหนถูกจำกัดเวลาเลย** รายงานเวลาจะว่าง |

| `set_false_path` | ตัดเส้นทางรีเซ็ตแบบ asynchronous | เส้นทางรีเซ็ตจะไปกวนการวิเคราะห์และอาจรายงานผิดพลาด |

### 2.4.3 ตรวจสอบว่าจำกัดครบแล้วหรือยัง

### 2.4.4 เทียบ SDC กับ XDC ใน Vivado

### 2.6.3 ตัวเลือกที่ควรรู้จัก

| ตัวเลือก | ผลต่อ QoR | ใช้เมื่อ |
|---|---|---|
| **Retiming** (เปิด/ปิด) | ย้ายรีจิสเตอร์ข้ามตรรกะ combinational เพื่อลดความหน่วงของเส้นทาง | ต้องการปรับปรุงเวลาแต่ไม่อยากเพิ่มจำนวนรีจิสเตอร์ |
| **Optimization effort** (ต่ำ/กลาง/สูง) | ยิ่งสูงยิ่งใช้เวลานานแต่ QoR ดีขึ้น | มีเวลาให้ลองหลายรอบเมื่อปิดเวลาไม่ผ่าน |
| **Resource sharing** | ลดจำนวนตัวคูณ/ตัวบวก | พื้นที่สำคัญกว่าเวลา |
| **Area optimization** | ลดพื้นที่ แลกกับเวลาที่ช้าลง | พื้นที่เป็นข้อจำกัดหลัก |

> **ข้อควรระวังเรื่อง Retiming**: การย้ายรีจิสเตอร์ข้ามขอบเขตโมดูลหรือข้ามพอร์ต I/O
> จะเปลี่ยนสมมติฐานของเส้นทาง I/O ทำให้เงื่อนไข SDC ที่เขียนไว้อาจไม่ตรงกับโครงสร้างใหม่
> ให้ตรวจรายงานเส้นทางหลังเปิด Retiming อีกครั้งเสมอ

## 3.1 สร้างความเข้าใจเรื่อง slack ก่อน

### 3.1.1 slack คืออะไร

**slack คือเวลาที่ "เหลือ" หลังจากทุกอย่างเสร็จ**

```text
คาบเวลานาฬิกา (period)      = 10.000 ns
- เวลาที่ต้องใช้ในเส้นทาง     =  8.200 ns
------------------------------------
= slack                      = +1.800 ns   ← ผ่าน มีเวลาเหลือ

คาบเวลานาฬิกา (period)      = 10.000 ns
- เวลาที่ต้องใช้ในเส้นทาง     = 11.400 ns
------------------------------------
= slack                      = -1.400 ns   ← ไม่ผ่าน เกินไป 1.4 ns
```

| ค่า | ความหมาย | ต้องทำอะไร |
|---|---|---|
| slack > 0 | ผ่าน มีเวลาสำรอง | ยิ่งมากยิ่งดี (มี headroom รับความไม่แน่นอนของการเดินสาย) |
| slack = 0 | ผ่านแบบเป๊ะ | เสี่ยงมาก ความคลาดเคลื่อนเล็กน้อยก็ทำให้ไม่ผ่าน |
| slack < 0 | ไม่ผ่าน (violation) | ต้องลดเวลาเส้นทางให้สั้นลงอย่างน้อยเท่ากับ \|slack\| |

### 3.1.2 setup slack กับ hold slack ต่างกันอย่างไร

| | Setup slack | Hold slack |
|---|---|---|
| ความหมาย | ข้อมูลมาถึงรีจิสเตอร์ **ทันเวลา** ก่อนขอบปิดของนาฬิกา | ข้อมูลมาถึงรีจิสเตอร์ **ไม่เร็วเกินไป** หลังขอบเปิดของนาฬิกา |
| ปัญหาที่พบบ่อย | เส้นทางยาวเกินคาบเวลา | เส้นทางสั้นเกินไป |
| แก้ด้วย | เพิ่มรอบนาฬิกา ลดตรรกะ เพิ่ม pipeline | เพิ่มความหน่วง (insert buffer/delay) |
| ตรวจได้แม่นเมื่อ | หลังสังเคราะห์ | **หลังเดินสายเท่านั้น** |

> **ข้อควรระวังที่สำคัญที่สุดของบทนี้**
> รายงาน **hold** จากขั้นสังเคราะห์ของ PS **ยังไม่น่าเชื่อถือ** เพราะยังไม่มีข้อมูล
> ความหน่วงการเดินสายจริง ซึ่งเป็นตัวแปรที่ทำให้ hold violation เกิดขึ้นบ่อยที่สุด
> **ต้องตรวจ hold อีกครั้งหลัง route ใน Vivado เสมอ** (บทที่ 4)

### 3.1.3 WNS และ TNS

| ตัวชี้วัด | ความหมาย | ใช้ทำอะไร |
|---|---|---|
| **WNS** (Worst Negative Slack) | slack ที่แย่ที่สุดของทุกเส้นทาง | ตัวเลขเดียวที่บอกว่า "ผ่านหรือไม่" |
| **TNS** (Total Negative Slack) | ผลรวม slack ของทุกเส้นทางที่เป็นลบ | บอกว่า "แย่แค่ไหน" — ยิ่งมากยิ่งต้องแก้หลายจุด |

กติกาที่ใช้ได้จริง: **WNS ≥ 0 และ TNS = 0** คือผ่าน

## 3.2 การอ่านรายงานเวลา

### 3.2.1 เปิดรายงาน

```text

หรือ

```

ให้เลือกจำนวนเส้นทางที่ต้องการดู (เช่น 20 เส้นทาง) เพื่อเห็นภาพรวม

### 3.2.2 โครงสร้างของรายงานหนึ่งเส้นทาง

```text
Path 1 : top_alu8/alu8 (posedge @ 10.000 ns)

  ------------------------------------------------------------------
  Startpoint : SW[3] (input)
  Endpoint   : top_alu8/y_r_reg[4] (posedge @ 20.000 ns)
  ------------------------------------------------------------------
  Slack      : 1.842 ns    ← ค่าที่ต้องดูเป็นอันดับแรก
  ------------------------------------------------------------------

  Delay   Cell      Description
  0.000  SW[3]     (input)   ─┐
  1.102  LUT       (A6, ...)  │ เส้นทางอินพุต → รีจิสเตอร์
  0.740  LUT       (B4, ...)  │ ตรรกะภายใน ALU
  0.000  y_r_reg[4] (capture) ─┘

  Total delay: 1.842 ns   จาก 23 ระดับตรรกะ
```

### 3.2.3 สิ่งที่ต้องสังเกตในรายงาน

| สิ่งที่ดู | บอกอะไร | นำไปใช้ทำอะไร |
|---|---|---|
| **Startpoint / Endpoint** | เส้นทางเริ่มและจบที่ไหน | บอกว่าปัญหาอยู่ที่ฝั่งอินพุต ฝั่งเอาต์พุต หรือภายใน |
| **Slack** | เหลือเวลาเท่าไร | ถ้าติดลบ ต้องแก้ที่เส้นทางนี้ก่อน |
| **จำนวนระดับตรรกะ (logic levels)** | ยิ่งมากยิ่งยากที่จะทำให้สั้นลง | ถ้าเยอะเกินจำเป็น แปลว่าโครงสร้างโค้ดไม่ดี |
| **เวลารวม** | ใช้เวลากี่นาน | เทียบกับคาบเวลา |
| **ชนิดเซลล์** | ใช้ LUT หรือ carry chain หรือ DSP | บอกว่า PS เลือกโครงสร้างอะไรให้ |

### 3.2.4 จุดสังเกตสำคัญ: เส้นทางที่ขาดนาฬิกา

```text
Startpoint : SW[3] (input)
Endpoint   : top_alu8/y_r_reg[4] (posedge @ 20.000 ns)
```

จุดสังเกตคือ **"posedge @ 10.000 ns"** หมายถึงมีนาฬิกากำกับอยู่
ถ้าเห็นข้อความแบบ

```text
Startpoint : SW[3] (input)
Endpoint   : top_alu8/y_r_reg[4] (no clock)
```

แปลว่าเส้นทางนี้ **ไม่ถูกจำกัดเวลา** ซึ่งไม่ควรเกิดขึ้น
ถ้าเกิด แปลว่า SDC ไม่ครบ หรือมีพอร์ตที่ไม่ได้กำหนดเวลา

### 3.3.3 วิธีอ่านที่ถูกต้อง

1. **ดูเปอร์เซ็นต์ ไม่ใช่จำนวนสัมบูรณ์** — ถ้าใช้ 2% ของ LUT ก็ยังมีที่ว่างเหลือเพียงพอ
2. **ดูทรัพยากรที่เป็นข้อจำกัด** — ถ้าใช้ LUT ไม่เต็มแต่ใช้ BRAM เต็ม ก็ต้องหาวิธีลด BRAM

   (Nexys A7-100T ใช้ XC7A100T จึงใช้ค่าข้างบนได้เลย)
4. **จำนวน LUT ที่ไม่ใช่ LUT4** — PS อาจรายงานเป็น LUT5/LUT6 หรือรวมเป็น LUT
   ต้องดูว่ารายงานนับอย่างไรก่อนเปรียบเทียบระหว่างรอบ

### 3.3.4 จุดที่ควรสังเกตเป็นพิเศษ

| สังเกต | ความหมาย |
|---|---|
| `CARRY4` มีจำนวนมาก | ตัวบวก/ตัวลบถูกสังเคราะห์เป็น carry chain — เป็นเรื่องดีสำหรับ FPGA |
| `DSP48E1` = 0 แต่มีตัวคูณ | PS อาจสังเคราะห์ตัวคูณเป็น LUT ซึ่งใช้ทรัพยากรมากกว่ามาก |
| จำนวน FF เพิ่มขึ้นมากเมื่อเปิด Retiming | ตัวสังเคราะห์ย้ายรีจิสเตอร์จำนวนมากเพื่อลดเวลา |

> **คำถามชวนคิด**: ในแล็บนี้มี `int8_mac.vhd` ที่มีตัวคูณ 8×8
> ลองเพิ่มเข้าโปรเจกต์แล้วสังเคราะห์ใหม่ ดูว่า PS เลือกใช้ DSP48E1 หรือไม่
> และถ้าไม่ใช้ เพราะอะไร (คำตอบที่คาดหวัง: ต้องเปิดตัวเลือกการสังเคราะห์ตัวคูณเป็น DSP)

## 3.4 เส้นทางที่ไม่ถูกจำกัด (unconstrained paths)

### 3.4.1 ทำไมต้องสนใจเส้นทางเหล่านี้มาก

เส้นทางที่ไม่ถูกจำกัดเวลา คือเส้นทางที่ **ตัวสังเคราะห์ไม่รู้ว่าต้องเร็วแค่ไหน**
ผลคือ

- ตัวสังเคราะห์จะไม่พยายามปรับปรุงเส้นทางนั้น → ได้ QoR ที่แย่
- รายงานเวลาจะไม่แสดงเส้นทางนี้ → คิดว่าผ่านทั้งที่จริง ๆ ไม่ได้ผ่าน
- เมื่อส่งต่อไป Vivado แล้วเพิ่งมีคนเห็นว่าเส้นทางนั้นพัง → เสียเวลาแก้ทีหลัง

### 3.4.2 ตรวจสอบ

```text
Report > Timing > Unconstrained Paths
```

หรือในสคริปต์

```tcl
report_timing -unconstrained_paths
```

### 3.4.3 สาเหตุที่พบบ่อย และวิธีแก้

| สาเหตุ | อาการ | วิธีแก้ |
|---|---|---|
| ลืมสร้างนาฬิกา | ทุกเส้นทางไม่ถูกจำกัด | `create_clock` |
| พอร์ตอินพุตไม่ได้ระบุเวลา | เส้นทางอินพุต → รีจิสเตอร์ ไม่ถูกจำกัด | `set_input_delay` |
| พอร์ตเอาต์พุตไม่ได้ระบุเวลา | เส้นทางรีจิสเตอร์ → เอาต์พุต ไม่ถูกจำกัด | `set_output_delay` |
| นาฬิกาที่สร้างจากนาฬิกาอื่น | เส้นทางของนาฬิกาที่ derive ไม่ถูกจำกัด | `create_generated_clock` |
| เส้นทางรีเซ็ต | รีเซ็ตไปยัง FF ไม่ถูกจำกัด | `set_false_path` |

### 3.4.4 สูตรจำ

> **ทุกเส้นทางที่เราสนใจต้องมีนาฬิกากำกับ**
> เส้นทางที่ "ไม่มีปัญหา" ก็ยังต้องถูกจำกัด เพราะการไม่ถูกจำกัดแปลว่า "เรายังไม่รู้"

## 3.5 ย้อนจาก critical path ใน schematic กลับไป HDL

นี่คือความสามารถที่คู่มือ PS2018.1 ชูในข้อ 3a และเป็นจุดขายหลักของ PS

### 3.5.1 ภาพรวมของการย้อนกลับ

```text
รายงานเวลา (ระบุเซลล์ที่วิกฤต)
        │
        ▼
Schematic viewer (เห็นโครงสร้างตรรกะรอบเซลล์ที่วิกฤต)
        │
        ▼ เลือกเซลล์แล้วสั่งให้แสดงต้นทาง
โค้ด HDL ต้นทาง (บรรทัดที่เขียนตรรกะนั้น)
```

### 3.5.2 วิธีทำใน PS

**ขั้นที่ 1 — เปิด schematic ของเส้นทางวิกฤต**

```text
Report > Timing > Critical Path
คลิกขวาที่เส้นทางที่ต้องการ > View Schematic
```

หรือเปิด schematic ของทั้งดีไซน์แล้วเลื่อนไปยังเซลล์ที่ระบุในรายงาน

**ขั้นที่ 2 — เลือกเซลล์ที่ต้องการ**

คลิกเซลล์ใน schematic จะเปิดหน้าต่างคุณสมบัติของเซลล์ ซึ่งแสดง

- ชนิดเซลล์และพิน
- ความหน่วงที่ประเมินได้
- **ต้นทางของเซลล์ (cell origin)** — เซลล์ใดในตรรกะเดิมที่ถูกยุบรวมมาเป็นเซลล์นี้

**ขั้นที่ 3 — ไปที่โค้ดต้นทาง**

เมื่อเลือกเซลล์แล้ว ใช้คำสั่งแสดงต้นทางในโค้ด HDL

```text
คลิกขวาที่เซลล์ > Show Source (หรือ Locate in Source / Trace to Source)
```

*ชื่อเมนูอาจต่างกันเล็กน้อยตามรุ่น — ให้เลือกจากเมนูที่มีอยู่จริง
(ตรวจสอบกับเอกสารของรุ่นที่ใช้)*

ผลลัพธ์คือหน้าต่างแสดงโค้ด VHDL พร้อมเครื่องหมายบรรทัดที่สร้างตรรกะนั้น

### 3.5.3 วิธีทางเลือกที่ใช้ได้เสมอ — อ่านจากรายงาน

รายงานเวลาของ PS มักระบุ **บรรทัดของโค้ดต้นทาง** ในแต่ละขั้นของเส้นทาง
วิธีนี้ไม่ต้องพึ่ง schematic viewer และใช้ได้แม้ไม่มี GUI

```text
  Delay   Cell          Description              Source
  0.000  SW[3]         (input)
  1.102  LUT (A6)      alu8.vhd:118             ← บรรทัดที่สร้างตรรกะ
  0.740  LUT (B4)      alu8.vhd:126
  0.000  y_r_reg[4]    (capture)                 top_alu8.vhd:95
```

จากนี้ผู้เรียนเปิดไฟล์ที่ระบุแล้วไปที่บรรทัดนั้นได้ทันที

### 3.5.4 วิธีทางเลือกที่สาม — ใช้ Vivado ช่วย

เมื่อส่งต่อไป Vivado แล้ว Vivado มี cross-probe ที่ชัดเจนมาก

```text
Report > Report Timing
คลิกขวาที่เซลล์ในรายงาน > Open Synthesized Design
แล้วในหน้าต่าง Schematic:
  คลิกขวาที่เซลล์ > Open Source
```

> ข้อดีของการใช้ Vivado ช่วยคือมีโค้ดต้นทาง (RTL) อยู่ในโปรเจกต์เต็มรูปแบบ
> จึงเปิดไฟล์ต้นทางและแสดงตำแหน่งบรรทัดได้ทันที
> เหตุผลที่ควรเก็บ RTL ไว้ในโปรเจกต์ Vivado เสมอ แม้จะรับ EDIF มาก็ตาม

### 3.5.5 ตัวอย่างการวิเคราะห์ critical path จริง

สมมติรายงานเวลาชี้ว่า

```text
Startpoint : SW[15:8] (input)
Endpoint   : top_alu8/y_r_reg[7] (posedge @ 10.000 ns)
Slack      : -0.230 ns
  1.842  LUT   alu8.vhd:118   ← ตัวบวกขั้นแรก
  1.210  LUT   alu8.vhd:126   ← ตัวบวกขั้นสอง
  0.980  LUT   alu8.vhd:118
  ...
```

**ลำดับการคิด**

1. เส้นทางนี้คืออินพุต → รีจิสเตอร์ แปลว่าเป็น **เส้นทางขาอินพุต** ไม่ใช่ขาเอาต์พุต
2. slack ติดลบ 0.23 ns แปลว่าเกินมาเล็กน้อย
3. ตรรกะทั้งหมดอยู่ใน `alu8.vhd` บรรทัด 118–126 คือส่วนของตัวบวก/ตัวลบ
4. ทางเลือกในการแก้:
   - ถ้าเส้นทางนี้สำคัญมาก → ลดความกว้างบิตของ ALU (ไม่ใช่ทางเลือกที่ดีในทางปฏิบัติ)
   - ถ้าเกิดจาก carry chain ที่ยาว → ดูว่า PS ได้ใช้ carry chain หรือยัง
   - ลดเวลาที่ใช้กับอินพุต: `set_input_delay` ลดลงเป็น 1.5 ns จะได้ slack เพิ่ม 0.5 ns
   - เพิ่มรอบนาฬิกา (ไม่ได้ในบอร์ดนี้ เพราะนาฬิกาหลักคือ 100 MHz)
   - ลดจำนวนชั้นของตรรกะ: เพิ่ม pipeline stage ใน RTL (เปลี่ยนโค้ด ไม่ใช่แก้ที่เครื่องมือ)

> **บทเรียน**: เมื่อปัญหาอยู่ที่ตรรกะ การแก้ที่เครื่องมือมีขีดจำกัด
> การย้อนกลับไปที่โค้ด HDL คือวิธีที่ยั่งยืนกว่าการไล่ปรับตัวเลือกของเครื่องมือไปเรื่อย ๆ

## 3.8 สรุปบท

- slack = เวลาที่เหลือ ต้อง ≥ 0; WNS ≥ 0 และ TNS = 0 คือผ่าน
- setup ต้องตรวจหลังสังเคราะห์ได้ แต่ **hold ต้องตรวจหลังเดินสาย**
- ทุกเส้นทางที่เราสนใจต้องถูกจำกัดเวลา ไม่มีข้อยกเว้น

## 4.1 ทำไมต้องส่งต่อ

| งาน | ใครทำ | เหตุผล |
|---|---|---|
| สังเคราะห์ RTL → เน็ตลิสต์ | Precision | เลือกไลบรารีของอุปกรณ์ได้, วิเคราะห์ QoR ได้ละเอียด |
| เลือกอุปกรณ์และตั้งค่าเงื่อนไข | Precision | รวมไว้ในขั้นตอนเดียว |
| วางวาง (place) | Vivado | ต้องใช้ข้อมูลภายในของอุปกรณ์ที่ครบถ้วน |
| ปรับแต่งการเดินสาย (phys_opt) | Vivado | ต้องเห็น routing จริง |
| เดินสาย (route) | Vivado | เป็นขั้นตอนที่ให้คำตัดเวลา |
| ตรวจ DRC และสร้าง bitstream | Vivado | ต้องใช้ตัวสร้าง bitstream ของผู้ผลิต |

**ข้อสรุป**: ตัวเลขเวลาที่ "ผ่าน" จริง ๆ ต้องมาจาก Vivado หลัง route เสร็จเท่านั้น

## 4.2 สิ่งที่ต้องส่งต่ออะไรบ้าง

| สิ่งที่ส่ง | รูปแบบ | ทำหน้าที่ |
|---|---|---|
| เน็ตลิสต์ตรรกะ | **EDIF** (`.edif`) | โครงสร้างวงจรที่สังเคราะห์แล้ว พร้อมชื่อเซลล์จริง |
| ข้อจำกัดการจัดวางพิน | **XDC** (`.xdc`) | ผูกพอร์ตกับพินจริงบนบอร์ด |

| ขั้นตอนการทำงาน | **Tcl** (`.tcl`) | สั่ง place/route/report อัตโนมัติ |
| ข้อกำหนดอุปกรณ์ | part / board part | บอก Vivado ว่าสร้างสำหรับชิปอะไร |

> และ "ต้องเร็วแค่ไหน" ขาดส่วนใดส่วนหนึ่งไม่ได้

## 4.4 เกณฑ์ตรวจรับงาน (sign-off gate) ก่อนสร้าง bitstream

### 4.4.1 เกณฑ์มาตรฐาน

| เกณฑ์ | ค่าที่ต้องการ | ตรวจที่ไหน |
|---|---|---|
| Setup timing | WNS ≥ 0 และ TNS = 0 | `Report > Timing Summary` |
| Hold timing | WNS ≥ 0 และ TNS = 0 | `Report > Timing Summary` (ส่วน min delay) |
| Unconstrained paths | 0 | `Report > Clock Interaction` |
| DRC error | 0 | `Report > DRC` |
| เงื่อนไขครบถ้วน | ไม่มี critical warning ว่าพอร์ตไม่ถูกจำกัด | `Report > Methodology` |

### 4.4.2 สคริปต์ตรวจอัตโนมัติ

ไฟล์ `labs/vivado/check_signoff.tcl` ทำหน้าที่ดังนี้

```tcl
proc worst_slack {dt} {
    set paths [get_timing_paths -delay_type $dt -max_paths 1 -nworst 1]
    if {[llength $paths] == 0} { return "NA" }
    return [get_property SLACK [lindex $paths 0]]
}

set setup_slack [worst_slack max]
set hold_slack  [worst_slack min]

set unconstrained [get_timing_paths -unconstrained -nworst 100]
set n_unconstrained [llength $unconstrained]

set drc_text [report_drc -return_string]
set n_drc_error [regexp -count -nocase {ERROR} $drc_text]
```

แล้วตรวจเงื่อนไขและเขียนรายงาน

```text
Sign-off report
================================================
setup slack (worst) : 0.831 ns
hold  slack (worst) : 0.124 ns
DRC errors          : 0
unconstrained paths : 0
------------------------------------------------
RESULT: PASS
```

ถ้าไม่ผ่าน สคริปต์จะ **ไม่สร้าง bitstream** และจบด้วยข้อความแสดงเหตุผล

```text
RESULT: FAIL
  - setup slack -0.230 < 0.0
```

### 4.4.3 การตีความเมื่อไม่ผ่าน

| อาการ | สาเหตุที่เป็นไปได้ | ทางแก้ |
|---|---|---|
| Setup ไม่ผ่าน | เวลาจริงหลังเดินสายนานกว่าที่คาด | ปรับ RTL / เพิ่ม effort / ใช้ phys_opt |
| Hold ไม่ผ่าน | เส้นทางสั้นเกินไปหลังเดินสาย | ใส่ delay buffer, `phys_opt_design -directive` |
| DRC error | ขัดแย้งกับข้อกำหนดการจัดวาง | แก้ XDC เช่น พินชนกัน |
| Unconstrained > 0 | พอร์ตที่ไม่ได้จำกัดเวลา | เติมเงื่อนไขใน XDC |

> **บทเรียนสำคัญ**: งานที่ผ่านทุกเกณฑ์หลัง route มักจะผ่านได้
> แต่งานที่ "ผ่าน" หลังสังเคราะห์อย่างเดียว อาจพังตอน route
> เพราะ **ความหน่วงการเดินสายจริงอาจมากกว่าที่คาดไว้หลายเท่า**

## 4.5 ตรวจ hold violation และแก้

hold เป็นปัญหาที่ **ต้องแก้หลังเดินสาย** เพราะต้องรู้ความหน่วงจริงของสาย

### 4.5.1 วิธีตรวจ

```text
Report > Report Timing Summary
  ดูส่วน "Min Delay" / ช่อง "WNS(ns)" ในตาราง "Intra Clock Table"
  หรือ
Report > Report Timing
  เลือก "Hold" / delay_type = min
```

### 4.5.2 วิธีแก้ตามลำดับที่เหมาะสม

1. **ให้ Vivado แก้เองก่อน** — `phys_opt_design` มีกลไกจัดการ hold อัตโนมัติ
2. **ปรับ directive**

   ```tcl
   phys_opt_design -directive AggressiveFanoutOpt
   ```

3. **ใส่ delay buffer เอง** — เพิ่มเซลล์หน่วงในเส้นทางที่สั้นเกินไป
4. **ตัดเส้นทางที่ไม่จำเป็นด้วย `set_false_path`** — ใช้ได้เฉพาะกรณีที่แน่ใจว่าไม่มีความเสี่ยง
   (เช่นเส้นทางข้อมูลที่ไม่มีเงื่อนไขการถือครองข้อมูล)

> **ข้อควรระวัง**: การใช้ `set_false_path` เพื่อ "แก้" hold ที่เกิดจริง
> คือการซ่อนปัญหา ไม่ใช่การแก้ ต้องใช้เฉพาะเมื่อมีเหตุผลทางระบบรองรับ

### 4.6.2 วิธีทดสอบบน Nexys A7-100T

| ทดสอบ | วิธีทำ | ผลที่คาดหวัง |
|---|---|---|
| นาฬิกา | ดูจอ 7 ส่วนเปลี่ยนไปเรื่อย ๆ | เปลี่ยนประมาณ 1,526 ครั้งต่อวินาที (100 MHz ÷ 2¹⁶) |
| ตัวคำนวณ | ตั้ง SW[7:0] = 5, SW[15:8] = 3, BTN = ADD | LED[7:0] แสดง 8 (0x08) บนจอแสดง "08" |

ถ้าตาไม่จับได้แม้แต่กะพริบ แสดงว่าตัวนับหรือนาฬิกามีปัญหา — ให้ตรวจรายงาน timing ของเส้นทางนั้น

## 4.7 แนวทางสำรองเมื่อ EDIF ใช้ไม่ได้

อาจพบปัญหาที่ Vivado อ่าน EDIF ที่ส่งมาจาก PS ไม่ได้ เนื่องจากปัญหาเรื่องชื่อเซลล์
หรือไลบรารี มีแนวทางสำรอง 3 ทาง เรียงตามลำดับความสะดวก

| ทาง | วิธี | ข้อดี/ข้อเสีย |
|---|---|---|
| **1** | ให้ PS ส่งเน็ตลิสต์เป็น **VHDL/Verilog** แล้วให้ Vivado อ่านเป็น source | ง่าย แต่เสียข้อได้เปรียบของการใช้ไลบรารีอุปกรณ์ใน PS |
| **2** | เก็บ RTL ไว้ในโปรเจกต์ Vivado แล้วให้ Vivado สังเคราะห์เอง | ได้ debug ง่าย แต่ไม่ได้ทดสอบคุณภาพของเน็ตลิสต์จาก PS |
| **3** | ตรวจไลบรารีที่ PS ใช้ แล้วจัดการให้ถูกต้อง | แก้ที่ต้นเหตุ แต่ต้องเข้าใจรูปแบบ EDIF ของอุปกรณ์ |

> **คำแนะนำสำหรับการอบรม**: ให้ทำแบบทาง 2 ควบคู่กับทาง 1 เสมอ
> เพราะผลลัพธ์ของบทที่ 5 (เปรียบเทียบ 10 ns กับ 8 ns) ต้องเปรียบเทียบ
> **เน็ตลิสต์ที่สังเคราะห์ด้วยเป้าหมายต่างกัน** ถ้าให้ Vivado สังเคราะห์ใหม่ทั้งคู่
> ก็จะไม่ได้ทดสอบสิ่งที่ต้องการทดสอบจริง

**เกณฑ์ผ่าน**: เข้าใจว่ากลไกการแก้ hold ของ Vivado ทำงานอย่างไร

---

## 4.9 สรุปบท

- สิ่งที่ส่งต่อ Vivado มี 4 อย่าง: EDIF (วงจร), XDC (พิน + เวลา), part, และขั้นตอน Tcl
- เกณฑ์ sign-off ต้องตรวจ 4 อย่าง: setup, hold, unconstrained paths, DRC
- **hold ตรวจได้จริงหลัง route เท่านั้น**
- ควรเก็บ RTL ในโปรเจกต์ Vivado ไว้เสมอ เพื่อการ debug และการทำ cross-probe
- สคริปต์เกณฑ์ sign-off ทำให้กระบวนการ "ตรวจก่อนปล่อย" เป็นระบบ ไม่ต้องพึ่งความจำ

**เตรียมตัวก่อนบทถัดไป**: มีผล post-route รอบ 10 ns และ 8 ns สำหรับเปรียบเทียบ (บทที่ 5)

# บทที่ 5 — ทดลองเปรียบเทียบ QoR: เป้าหมายสังเคราะห์ 10 ns กับ 8 ns

> **เป้าหมายของบทนี้**: ให้ผู้เรียนพิสูจน์ด้วยตัวเองว่า **"ยิ่งบีบเวลาให้เข้ม ยิ่งได้ผลดีขึ้น" เป็นความเข้าใจผิด**
> และรู้ว่าการประเมิน QoR ที่ถูกต้อง ต้องประเมิน **หลัง routing** ด้วย **เงื่อนไขของบอร์ดจริง**
> เสมอ ไม่ใช่เงื่อนไขที่ตั้งไว้ตอนสังเคราะห์

---

## 5.1 ปัญหาที่กำลังศึกษา

บอร์ด Nexys A7-100T มีนาฬิกาหลัก **100 MHz** คือคาบเวลา **10 ns**

สมมติว่าทีมงานต้องการ "ประกันความเร็ว" มากกว่านั้น จึงตั้งเป้าหมายสังเคราะห์เป็น **8 ns**
(คิดเป็น 125 MHz) โดยตั้งสมมติฐานว่า "ยิ่งบีบเวลา ยิ่งได้ดีไซน์ที่เร็วกว่าและปลอดภัยกว่า"

**คำถามของการทดลองนี้คือ**: สมมติฐานนั้นจริงหรือไม่ เมื่อวัดจากผลจริงหลังเดินสาย?

---

## 5.2 ทฤษฎี: การบีบเวลาทำอะไรกับตัวสังเคราะห์

### 5.2.1 สิ่งที่ตัวสังเคราะห์ทำเมื่อเป้าหมายเข้มขึ้น

เมื่อบีบเวลาที่ต้องการ ตัวสังเคราะห์จะพยายามลดความหน่วงของเส้นทางวิกฤตด้วยวิธีต่อไปนี้
**เรียงตามลำดับที่มักถูกใช้**

| # | วิธี | ผลต่อเวลา | ผลต่อพื้นที่ | ผลข้างเคียง |
|---|---|---|---|---|
| 1 | เปลี่ยนโครงสร้างตรรกะให้สั้นลง | ดีขึ้นมาก | เพิ่มขึ้น | ตรรกะซับซ้อนขึ้น อาจเพิ่มพื้นที่มาก |
| 2 | ทำซ้ำ (duplicate) ตรรกะที่ใช้ร่วมกัน | ดีขึ้น | เพิ่มขึ้น | โครงสร้างฟิสิกส์เปลี่ยน ต้องวางวางใหม่ |
| 3 | ใส่รีจิสเตอร์เพิ่ม (pipeline) | ดีขึ้นมาก | เพิ่มขึ้นมาก | **เปลี่ยนสมมติฐานของเส้นทาง I/O** ต้องแก้ SDC |
| 4 | ย้ายรีจิสเตอร์ (retiming) | ดีขึ้น | เพิ่ม/ลดเล็กน้อย | เปลี่ยนโครงสร้างขอบเขตรีจิสเตอร์ |
| 5 | เปลี่ยนตัวเลือกของการแมปเซลล์ | ดีขึ้นเล็กน้อย | เพิ่มเล็กน้อย | ต้องเลือกเซลล์ที่วางวางยากขึ้น |

### 5.2.2 ผลข้างเคียงที่สำคัญที่สุด — "ความแย่ลงจากการวางวาง"

นี่คือประเด็นแกนกลางของบทนี้

```text
เป้าหมายเข้มขึ้น
      │
      ▼
ตรรกะซับซ้อนขึ้น / เซลล์เฉพาะทางมากขึ้น
      │
      ▼
ความหน่วงการเดินสายเพิ่มขึ้น (routing delay เพิ่ม)
      │
      ▼
พื้นที่ที่ใช้มากขึ้น → ความแน่นของการวางวางเพิ่ม
      │
      ▼
เส้นทางที่ "ดี" ตอนสังเคราะห์ อาจกลายเป็น "แย่" หลังวางวาง
```

ดังนั้นตัวเลขที่ PS รายงานหลังสังเคราะห์ **ไม่ใช่ตัวชี้วัดคุณภาพสุดท้าย**
แต่เป็นเพียงตัวชี้วัด "ความพยายามของตัวสังเคราะห์ในการตอบสนองต่อคำสั่งของเรา"

### 5.2.3 กรณีที่การบีบเวลา "ถูกต้อง"

การบีบเวลาไม่ได้ผิดเสมอไป มีกรณีที่เหมาะสม

| กรณี | เหตุผล |
|---|---|
| บอร์ดมีนาฬิกาเร็วกว่านี้จริง | ต้องการประสิทธิภาพที่ 125 MHz จริง ๆ |
| ต้องการ headroom สำหรับอุณหภูมิ/แรงดันที่แตกต่างกัน | เผื่อ margin ไว้ |
| ยังไม่รู้ความถี่ปลายทาง | ตั้งค่าขั้นต่ำไว้ก่อนเพื่อคุ้มค่า |
| การทำงานแบบ timing closure | ต้องการให้ตัวสังเคราะห์ทำงานหนักขึ้น |

แต่ในกรณีของบอร์ด Nexys A7-100T ที่มีนาฬิกา 100 MHz การตั้ง 8 ns **ไม่ใช่ข้อกำหนดของฮาร์ดแวร์**
เป็นการตั้งที่ "เข้มกว่าที่จำเป็น" ซึ่งเป็นหัวข้อของการทดลองนี้

## 5.3 วิธีทำการทดลอง

### 5.3.1 หลักการควบคุมตัวแปร

การทดลองที่ดีต้องเปลี่ยน**เฉพาะ**ตัวแปรที่ศึกษา ดังนั้นให้ตรวจสอบว่า

| ตัวแปร | ค่า | เหมาะสมไหม |
|---|---|---|
| ไฟล์ RTL | เหมือนกันทั้งสองรอบ | ✔ ต้องเหมือนกันเด็ดขาด |
| ไลบรารีอุปกรณ์ | เหมือนกัน | ✔ |
| ตัวเลือก Retiming | เหมือนกัน | ✔ |
| Optimization effort | เหมือนกัน | ✔ |
| สคริปต์ Vivado | เหมือนกัน | ✔ |
| **SDC ตอนสังเคราะห์** | **10 ns กับ 8 ns** | ← ตัวแปรที่ศึกษา |
| **เงื่อนไขตอนประเมิน** | **10 ns ทั้งสองรอบ** | ← ตัวแปรที่ควบคุม |

> **ประเด็นสำคัญที่สุดของบทนี้**
> เมื่อนำเน็ตลิสต์ทั้งสองรอบไป Vivado **ต้องประเมินด้วยคาบเวลา 10 ns เท่ากัน**
> เพราะ 10 ns คือคาบเวลาจริงของบอร์ด คำตอบคือ "ดีไซน์ไหนทำงานได้ดีกว่า **บนบอร์ดตัวจริง**"
> ไม่ใช่ "ดีไซน์ไหนบรรลุเป้าหมายที่ตั้งไว้ตอนสังเคราะห์"

### 5.3.2 ขั้นตอน

**รอบ A — เป้าหมาย 10 ns**

```bash
# Precision
ps_shell -f ps_qor_10ns.tcl
# ผลลัพธ์: out_10ns/top_alu8.edif, out_10ns/timing.rpt, out_10ns/area.rpt

# Vivado: ประเมินด้วยคาบเวลา 10 ns
vivado -mode batch -source run_pnr.tcl   # โดยแก้ edif_file เป็น out_10ns/top_alu8.edif
```

**รอบ B — เป้าหมาย 8 ns**

```bash
ps_shell -f ps_qor_8ns.tcl
# ผลลัพธ์: out_8ns/top_alu8.edif, out_8ns/timing.rpt, out_8ns/area.rpt

vivado -mode batch -source run_pnr.tcl   # โดยแก้ edif_file เป็น out_8ns/top_alu8.edif
# และยืนยันว่า XDC ยังเป็นคาบเวลา 10.000 ns
```

**สำคัญ**: ใน Vivado ต้องใช้ XDC เดิม (10 ns) ทั้งสองรอบ
ถ้าใช้ XDC 8 ns กับเน็ตลิสต์รอบ B จะเป็นการประเมินคนละโจทย์ ซึ่งไม่ตอบคำถามที่ต้องการ

### 5.3.3 สิ่งที่ต้องบันทึก

ใช้ตารางใน `labs/results/qor_results_template.md` โดยบันทึก

**จาก Precision (pre-route)**

- setup slack วิกฤต, จำนวนเส้นทางที่ slack < 0
- จำนวนระดับตรรกะของเส้นทางวิกฤต
- LUT, FF, BRAM, DSP และพื้นที่รวม
- จำนวนเส้นทางที่ไม่ถูกจำกัด

**จาก Vivado (post-route, ประเมินที่ 10 ns)**

- WNS setup, TNS setup
- WNS hold, TNS hold
- เส้นทางวิกฤตที่รายงาน
- LUT/FF หลัง implement
- จำนวน DRC error/warning
- unconstrained paths

## 5.4 ผลตัวอย่างและการวิเคราะห์

> ตัวเลขต่อไปนี้เป็น **ตัวอย่างเพื่ออธิบายแนวคิด** ไม่ใช่ผลจากการรันจริง
> ให้ใช้ตัวเลขของตัวเองในการสรุปผล

### 5.4.1 ผลหลังสังเคราะห์ (pre-route)

| ตัวชี้วัด | รอบ A: 10 ns | รอบ B: 8 ns | ผลต่าง | อธิบาย |
|---|---|---|---|---|
| Setup slack วิกฤต | +1.42 ns | +0.55 ns | −0.87 ns | slack ลดลงเพราะ "เป้าหมาย" เข้มขึ้น ไม่ได้แปลว่าเส้นทางยาวขึ้น |
| ระดับตรรกะ | 6 | 5 | −1 | PS ย้ายรีจิสเตอร์หรือยุบตรรกะให้สั้นลง |
| LUT | 148 | 176 | +18.9% | ต้องใช้ตรรกะมากขึ้นเพื่อย่อเส้นทาง |
| FF | 61 | 74 | +21.3% | เพิ่มรีจิสเตอร์ระหว่างทาง |
| Unconstrained | 0 | 0 | 0 | ทั้งสองรอบต้องมี SDC ครบ |

### 5.4.2 ผลหลัง routing (ประเมินที่ 10 ns ทั้งสองรอบ)

|---|---|---|---|---|

| TNS setup | 0 | 0 | 0 | ไม่มีเส้นทางลบในทั้งสองรอบ |

### 5.4.3 ข้อสรุปจากตัวอย่าง

1. **รอบ B ไม่ได้ดีกว่าในความหมายที่สำคัญ**
   แม้รอบ B จะมี slack ที่รายงานหลังสังเคราะห์ดีขึ้น (+0.55 ns เทียบกับ +1.42 ns)
   แต่เมื่อวัดที่คาบเวลาจริงของบอร์ด รอบ B แย่กว่าเล็กน้อย (+0.71 เทียบกับ +0.83 ns)

2. **รอบ B จ่ายค่าด้วยพื้นที่เพิ่มขึ้นราว 20%**
   ซึ่งในโปรเจกต์จริงที่มีดีไซน์อื่นอยู่ในชิป พื้นที่ที่เพิ่มขึ้นนี้อาจเป็นปัญหาจริง

3. **ตัวเลข pre-route ไม่ได้ทำนายผล post-route ได้แม่น
   การรายงาน slack หลังสังเคราะห์ของรอบ B ดู "ดี" ในเชิงเปอร์เซ็นต์
   แต่เพราะเป้าหมายต่างกัน จึงเปรียบเทียบกันโดยตรงไม่ได้

4. **บทเรียนที่ใช้ได้ทุกโปรเจกต์**
   ตั้งเป้าหมายสังเคราะห์ให้ **ตรงกับข้อกำหนดจริงของฮาร์ดแวร์**
   ไม่ใช่ตั้งให้เข้มที่สุดเท่าที่จะตั้งได้

## 5.5 วิธีตีความเมื่อผลออกมาต่างจากที่คาด

การทดลองนี้อาจได้ผลต่างจากตัวอย่าง และนั่นไม่ใช่เรื่องผิดปกติ เพราะผลขึ้นอยู่กับตัวสังเคราะห์ รุ่น และค่าคอนฟิก

| ผลที่ได้ | การตีความ |
|---|---|
| รอบ B ดีกว่าทั้งพื้นที่และเวลา | โอกาสเป็นไปได้น้อยมาก ตรวจว่าเงื่อนไขการประเมินเหมือนกันจริงหรือไม่ |
| รอบ B แย่กว่าทั้งสองอย่าง | เป็นกรณีที่พบบ่อยที่สุด สนับสนุนข้อสรุปในหัวข้อ 5.4.4 |

| รอบ B ทำให้เกิด hold violation | โครงสร้างที่ต่างออกไปอาจต้องการความหน่วงต่างจากเดิม ต้องแก้ที่ Vivado |
| ทั้งสองรอบมี unconstrained paths | กลับไปตรวจ SDC ก่อน — การทดลองนี้ใช้ไม่ได้ถ้าเงื่อนไขไม่ครบ |

## 5.6 แนวทางแก้ปัญหาเฉพาะของบทนี้

### 5.6.1 ปัญหา: รอบ B ใช้เวลาสังเคราะห์นานมาก

| สาเหตุ | วิธีแก้ |
|---|---|
| PS พยายามทำตามเป้าหมายที่เข้มมากจนต้องลองหลายวิธี | ลด Optimization effort ลง แต่ต้องใช้ค่าเดียวกันทั้งสองรอบ |
| เปิด Retiming ทำให้ต้องย้อนโครงสร้างหลายรอบ | ปิด Retiming ในทั้งสองรอบ หรือปล่อยเวลาไว้มากขึ้น |
| เครื่องไม่แรง | ลดขนาดดีไซน์ทดสอบ หรือใช้เครื่องที่แรงกว่า |

### 5.6.2 ปัญหา: ผล post-route แย่กว่า pre-route มาก

| สาเหตุ | วิธีแก้ |
|---|---|
| ใช้เงื่อนไขเวลาของรอบผิด (เช่น XDC 8 ns กับเน็ตลิสต์ 10 ns) | ตรวจว่า XDC เป็น 10.000 ns ทั้งสองรอบ |
| ไม่ได้กำหนด input/output delay | เส้นทาง I/O จะไม่ถูกจำกัดและรายงานจะเพี้ยน |
| `set_false_path` ผิดขอบเขต | ตรวจว่าไม่ได้ตัดเส้นทางที่ควรถูกจำกัด |

### 5.6.3 ปัญหา: เส้นทาง I/O เปลี่ยนพฤติกรรมระหว่างสองรอบ

ถ้า Retiming ทำให้รีจิสเตอร์ขยับข้ามพอร์ต I/O สมมติฐานของ SDC จะไม่ตรงอีกต่อไป
สังเกตได้จากรายงานของ PS ที่ Startpoint/Endpoint ของเส้นทางเปลี่ยนไป

> ที่ใช้ก่อน–หลังแต่ละขั้น ควรใช้เป็น "แผนกู้เมื่อติด" ในห้องเรียน

## 6.1 แนวทางวิเคราะห์ปัญหาแบบเป็นขั้นตอน

เมื่อมีปัญหา ให้ไล่จากข้างต้น (ต้นทาง) ไปปลายทางตามลำดับนี้
เพราะปัญหาเกือบทั้งหมดในงานสังเคราะห์จะอยู่ที่ขั้นตอนก่อนหน้าเสมอ

```text
1. RTL ถูกต้องไหม?          → ผ่าน testbench แล้วหรือยัง
2. เงื่อนไขเวลาครบไหม?        → มีเส้นทาง unconstrained หรือไม่
3. ตัวสังเคราะห์ผิดไหม?      → เทียบ pre-route กับค่าที่คาด
4. การวางวาง/เดินสายผิดไหม? → เทียบ post-route กับ pre-route
5. ส่งต่อระหว่างเครื่องมือผิดไหม? → เช็ค EDIF / XDC
6. ข้อจำกัดของชิปเกินไหม?   → utilization
```

## 6.2 ปัญหาระดับ RTL และการจำลอง

| อาการ | สาเหตุที่พบจริง | วิธีแก้ |
|---|---|---|
| ผลจำลองไม่ตรงกับผลสังเคราะห์ | process ที่ไวต่อ `clk` ขาด `rising_edge(clk)` | เพิ่ม `elsif rising_edge(clk) then` — ดูหัวข้อ 1.1.4 |
| ค่าผลลัพธ์เป็นสองเท่าที่ควรเป็น | ตัวสังเคราะห์/การจำลองทำงานทั้งขอบขึ้นและขอบลง | ตรวจทุก process ที่ sensitive กับ `clk` |
| ผลต่างกันเฉพาะคำสั่ง SUB | สลับลำดับ operand เพราะ `A & B` เอา A ไว้บิตสูง | สลับลำดับในการต่อสัญญาณ — ดูหัวข้อ 1.1.5 |
| ค่า overflow ไม่ตรง | ส่งค่า byte ดิบเข้าแบบจำลองที่ตีความแบบมีเครื่องหมาย | แปลงด้วย `int_of(byte_of(x))` ก่อนส่งเข้าแบบจำลอง |
| เกิด latch ในการจำลอง | ไม่ได้กำหนดค่าเริ่มต้นให้ทุกเอาต์พุต | ใส่ค่าเริ่มต้นก่อน `case` |
| ไฟล์ VHDL คอมไพล์ไม่ผ่าน | มีอักษรไทยใน string literal | ใช้ภาษาอังกฤษในข้อความ `report` — ดูหัวข้อ 1.3.3 |
| คอมไพล์ไม่ผ่าน "'others' choice not allowed" | ใช้ `(others => '0')` ใน expression | ใช้ constant — ดูหัวข้อ 1.3.3 |
| GHDL ขึ้น "invalid character not allowed" | พาธที่มีอักษรไทย | คัดลอกไปพาธ ASCII — ดูหัวข้อ 0.3.3 |
| handshake ตรวจผิดที่ | อ่านค่า signal หลังขอบขึ้น (post-edge) แทนก่อนขอบขึ้น | ใช้ process ที่ sensitive กับ `clk` และอ่านค่าในนั้น |
| testbench ไม่จบ | ไม่มีการเรียก `stop`/`finish` | เพิ่ม `stop` เมื่อผ่าน และ `assert false severity failure` เมื่อไม่ผ่าน |

## 6.3 ปัญหาระดับโปรเจกต์ Precision

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `Unable to find entity` | เพิ่มไฟล์มาผิดลำดับ | ลบออกแล้วเพิ่มใหม่ โดยเริ่มจาก leaf module |
| hierarchy ไม่ครบ | โมดูลในไฟล์เดียวกันไม่ถูกอ่าน | แยกแต่ละ entity ออกเป็นไฟล์ย่อย หรือตรวจรูปแบบไฟล์ |
| ไม่มีรายงานเวลาเลย | ยังไม่ได้ใส่ SDC หรือไม่ได้กำหนดความถี่ | ทำหัวข้อ 2.4 |
| รายงานเวลาเป็นศูนย์/ว่าง | ไม่มี clock ที่เกี่ยวข้อง | ตรวจ `create_clock` และชื่อพอร์ต |
| เส้นทางไม่ถูกจำกัดจำนวนมาก | ลืม `set_input_delay` / `set_output_delay` | ดูตารางในหัวข้อ 3.4.3 |
| ตัวเลขเวลาไม่สมจริง | ไม่ได้เลือกอุปกรณ์ | ตั้ง part ใน Environment Settings |
| ไม่พบ part ที่ต้องการ | รุ่นของ PS ไม่รองรับ | ใช้การสังเคราะห์แบบ generic หรือส่งเน็ตลิสต์ VHDL/Verilog — ดูหัวข้อ 2.3.4 |
| โปรเจกต์สังเคราะห์ไม่ซ้ำผลเดิม | ไม่ได้บันทึกค่าคอนฟิก | ใช้ `File > Save Command File` แล้วรันสคริปต์ |
| สังเคราะห์ช้าผิดปกติ | เปิด effort สูง หรือเปิด Retiming | ลด effort หรือปิด Retiming (แต่ต้องใช้ค่าเดียวกันทุกรอบที่เปรียบเทียบ) |

## 6.4 ปัญหาระดับการส่งต่อและ Place & Route

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| Vivado อ่าน EDIF ไม่ได้ | ชื่อเซลล์/ไลบรารีไม่ตรงกับอุปกรณ์ | ตรวจว่า PS ใช้ไลบรารีของอุปกรณ์ถูกตัว; ถ้าไม่ได้ให้ใช้ทางสำรองในหัวข้อ 4.7 |
| พอร์ตไม่ถูกผูกกับพิน | ไม่ได้ใส่ XDC | เพิ่ม `nexys_a7_100t.xdc` |

| Setup ไม่ผ่านหลัง route | เวลาเดินสายจริงมากกว่าที่ประมาณไว้ | ปรับ RTL, เพิ่ม effort, ใช้ phys_opt — ดูหัวข้อ 4.4.3 |

| Bitstream ที่ได้โปรแกรมไม่ขึ้น | ไฟล์ .bit ไม่ตรงกับบอร์ด หรือไม่ได้ตั้ง part | ตรวจ `xc7a100tcsg324-1` และความถี่โปรแกรมเมอร์ |
| บอร์ดแสดงผลผิด | RTL ผิด หรือสังเคราะห์จาก RTL คนละชุด | ตรวจว่าไฟล์ที่ใช้สร้าง bitstream ตรงกับที่ทดสอบ |

## 6.5 ปัญหาการเปรียบเทียบ QoR (บทที่ 5)

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| ผลของสองรอบเหมือนกันเป๊ะ | ลืมแก้ `sdc_file` ในสคริปต์ หรือสคริปต์ทั้งสองชี้ไฟล์เดียวกัน | ตรวจไฟล์ SDC ที่แต่ละรอบอ้างอิง |

## 6.8 สรุปบท

- ปัญหาเกือบทั้งหมดในงานสังเคราะห์อยู่ที่ขั้นก่อนหน้าเสมอ จึงควรไล่จากต้นทาง
- รายการตรวจสอบที่เขียนไว้ล่วงหน้า ช่วยลดเวลาที่ใช้แก้ปัญหาได้มากกว่าการจำจากหัว
- เกณฑ์ sign-off ที่ทำเป็นสคริปต์ ทำให้ "การตรวจก่อนปล่อย" เป็นกระบวนการมาตรฐาน
- คลังปัญหาของทีมเป็นทรัพย์สินที่ต้องสะสม เพราะปัญหาเดิมมักกลับมาในโปรเจกต์ถัดไป

**ขั้นตอนถัดไป**: ปิดท้ายการอบรมด้วยการทบทวนบทที่ 1–5 และส่งรายงานผลการทดลอง
พร้อมตารางบันทึกผล QoR ที่กรอกครบทุกช่อง

## ก.4 สคริปต์เกณฑ์ sign-off ฉบับสมบูรณ์

```tcl
# check_signoff.tcl
set min_setup_slack 0.0
set min_hold_slack  0.0
set max_drc_errors  0

proc worst_slack {dt} {
    set paths [get_timing_paths -delay_type $dt -max_paths 1 -nworst 1]
    if {[llength $paths] == 0} { return "NA" }
    return [get_property SLACK [lindex $paths 0]]
}

set setup_slack [worst_slack max]
set hold_slack  [worst_slack min]
set n_unconstrained [llength [get_timing_paths -unconstrained -nworst 100]]
set n_drc_error [regexp -count -nocase {ERROR} [report_drc -return_string]]

set signoff_ok 1
set reasons {}
if {$setup_slack eq "NA" || $setup_slack < $min_setup_slack} {
    lappend reasons "setup slack $setup_slack"; set signoff_ok 0 }
if {$hold_slack eq "NA" || $hold_slack < $min_hold_slack} {
    lappend reasons "hold slack $hold_slack"; set signoff_ok 0 }
if {$n_drc_error > $max_drc_errors} {
    lappend reasons "DRC errors $n_drc_error"; set signoff_ok 0 }
if {$n_unconstrained > 0} {
    lappend reasons "unconstrained paths $n_unconstrained"; set signoff_ok 0 }

set fh [open $out_dir/signoff_report.txt w]
puts $fh "setup slack (worst) : $setup_slack ns"
puts $fh "hold  slack (worst) : $hold_slack ns"
puts $fh "DRC errors          : $n_drc_error"
puts $fh "unconstrained paths : $n_unconstrained"
if {$signoff_ok} { puts $fh "RESULT: PASS" } else {
    puts $fh "RESULT: FAIL"
    foreach r $reasons { puts $fh "  - $r" } }
close $fh
```

# ภาคผนวก ข — ประจำศัพท์ไทย–อังกฤษ (Glossary)

จัดเรียงตามลำดับตัวอักษรภาษาอังกฤษ ค้นหาได้ทั้งคำไทยและคำอังกฤษ

---

## A

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| ASIC (Application-Specific Integrated Circuit) | วงจรรวมเฉพาะกิจ | ชิปที่ออกแบบมาเพื่องานเฉพาะทาง |
| Async reset | รีเซ็ตแบบไม่ประสานเวลา | รีเซ็ตที่ทำงานโดยไม่ต้องรอขอบนาฬิกา |
| AXI-Stream | — | โปรโตคอลส่งข้อมูลแบบสตรีมมิ่งที่ใช้ tvalid/tready |

## B

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| Backpressure | แรงดันย้อนกลับ | กลไกที่ผู้รับบอกผู้ส่งให้หยุดส่งชั่วคราว |
| Bitstream | บิตสตรีม | ไฟล์ที่เขียนลงชิป FPGA เพื่อกำหนดการทำงานของวงจร |
| Black box | กล่องดำ | โมดูลที่ทำงานถูกต้องแต่ไม่เห็นรายละเอียดภายใน |
| BRAM (Block RAM) | — | หน่วยความจำบล็อกภายใน FPGA |

## C

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| Clock skew | ความเบี่ยงเบนนาฬิกา | ความต่างของเวลาที่นาฬิกาไปถึงจุดต่าง ๆ ในวงจร |
| Congestion | ความแน่น | บริเวณที่มีการเชื่อมต่อหนาแน่นเกินไป ทำให้เดินสายยาก |
| Critical path | เส้นทางวิกฤต | เส้นทางที่ใช้เวลามากที่สุด กำหนดความเร็วของวงจร |
| Cross-probing | การเชื่อมข้าม | การคลิกที่วงจรแล้วเปิดโค้ดต้นทางทันที |

## D

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| DSP48E1 | — | หน่วยคูณสะสมสำเร็จใน FPGA ของ Xilinx 7-Series |
| DRC (Design Rule Check) | การตรวจกฎการออกแบบ | ตรวจข้อผิดพลาดของข้อจำกัดทางกายภาพ |
| DFF/DRE | ฟลิป-flop | รีจิสเตอร์เก็บค่า 1 บิต |

## E

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| EDIF (Electronic Design Interchange Format) | รูปแบบแลกเปลี่ยนข้อมูลอิเล็กทรอนิกส์ | มาตรฐานนำเน็ตลิสต์ของวงจร ใช้ส่งต่อระหว่างเครื่องมือ |
| Effort (optimization effort) | ความพยายามในการปรับปรุง | ปริมาณเวลาและทรัพยากรที่เครื่องมือใช้ในการปรับปรุง |
| Elaboration | การขยายตัว | กระบวนการสร้าง hierarchy และตรวจการเชื่อมต่อของโมดูล |

## F

| อังกฤษ | ไทย | คำอธิบาย |
|---|---|---|
| FIFO (First In First Out) | — | โครงสร้างข้อมูลแบบเข้าก่อนออกก่อน |
| Fix-up | การแก้ให้ถูกต้อง | การแก้ไขปัญหาที่พบระหว่างกระบวนการ |

## G
