# บทที่ 6 — แนวทางแก้ปัญหาและรายการตรวจสอบ

> บทนี้เป็นคลังปัญหาจริงที่พบระหว่างทำแล็บในคู่มือนี้ รวมถึงรายการตรวจสอบ
> ที่ใช้ก่อน–หลังแต่ละขั้น ควรใช้เป็น "แผนกู้เมื่อติด" ในห้องเรียน

---

## 6.1 แนวทางวิเคราะห์ปัญหาแบบเป็นขั้นตอน

เมื่อมีปัญหา ให้ไล่จากข้างต้น (ต้นทาง) ไปปลายทางตามลำดับนี้
เพราะปัญหาเกือบทั้งหมดในงานสังเคราะห์จะอยู่ที่ขั้นตอนก่อนหน้าเสมอ

```text
1. RTL ถูกต้องไหม?          → ผ่าน testbench แล้วหรือยัง
2. เงื่อนไขเวลาครบไหม?        → มีเส้นทาง unconstrained หรือไม่
3. ตัวสังเคราะห์ผิดไหม?      → เทียบ pre-route กับค่าที่คาด
4. การวางวาง/เดินสายผิดไหม? → เทียบ post-route กับ pre-route
5. ส่งต่อระหว่างเครื่องมือผิดไหม? → เช็ค EDIF / XDC
6. ข้อจำกัดของชิปเกินไหม?   → utilization
```

## 6.2 ปัญหาระดับ RTL และการจำลอง

| อาการ | สาเหตุที่พบจริง | วิธีแก้ |
|---|---|---|
| ผลจำลองไม่ตรงกับผลสังเคราะห์ | process ที่ไวต่อ `clk` ขาด `rising_edge(clk)` | เพิ่ม `elsif rising_edge(clk) then` — ดูหัวข้อ 1.1.4 |
| ค่าผลลัพธ์เป็นสองเท่าที่ควรเป็น | ตัวสังเคราะห์/การจำลองทำงานทั้งขอบขึ้นและขอบลง | ตรวจทุก process ที่ sensitive กับ `clk` |
| ผลต่างกันเฉพาะคำสั่ง SUB | สลับลำดับ operand เพราะ `A & B` เอา A ไว้บิตสูง | สลับลำดับในการต่อสัญญาณ — ดูหัวข้อ 1.1.5 |
| ค่า overflow ไม่ตรง | ส่งค่า byte ดิบเข้าแบบจำลองที่ตีความแบบมีเครื่องหมาย | แปลงด้วย `int_of(byte_of(x))` ก่อนส่งเข้าแบบจำลอง |
| เกิด latch ในการจำลอง | ไม่ได้กำหนดค่าเริ่มต้นให้ทุกเอาต์พุต | ใส่ค่าเริ่มต้นก่อน `case` |
| ไฟล์ VHDL คอมไพล์ไม่ผ่าน | มีอักษรไทยใน string literal | ใช้ภาษาอังกฤษในข้อความ `report` — ดูหัวข้อ 1.3.3 |
| คอมไพล์ไม่ผ่าน "'others' choice not allowed" | ใช้ `(others => '0')` ใน expression | ใช้ constant — ดูหัวข้อ 1.3.3 |
| GHDL ขึ้น "invalid character not allowed" | พาธที่มีอักษรไทย | คัดลอกไปพาธ ASCII — ดูหัวข้อ 0.3.3 |
| handshake ตรวจผิดที่ | อ่านค่า signal หลังขอบขึ้น (post-edge) แทนก่อนขอบขึ้น | ใช้ process ที่ sensitive กับ `clk` และอ่านค่าในนั้น |
| testbench ไม่จบ | ไม่มีการเรียก `stop`/`finish` | เพิ่ม `stop` เมื่อผ่าน และ `assert false severity failure` เมื่อไม่ผ่าน |

## 6.3 ปัญหาระดับโปรเจกต์ Precision

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `Unable to find entity` | เพิ่มไฟล์มาผิดลำดับ | ลบออกแล้วเพิ่มใหม่ โดยเริ่มจาก leaf module |
| hierarchy ไม่ครบ | โมดูลในไฟล์เดียวกันไม่ถูกอ่าน | แยกแต่ละ entity ออกเป็นไฟล์ย่อย หรือตรวจรูปแบบไฟล์ |
| ไม่มีรายงานเวลาเลย | ยังไม่ได้ใส่ SDC หรือไม่ได้กำหนดความถี่ | ทำหัวข้อ 2.4 |
| รายงานเวลาเป็นศูนย์/ว่าง | ไม่มี clock ที่เกี่ยวข้อง | ตรวจ `create_clock` และชื่อพอร์ต |
| เส้นทางไม่ถูกจำกัดจำนวนมาก | ลืม `set_input_delay` / `set_output_delay` | ดูตารางในหัวข้อ 3.4.3 |
| ตัวเลขเวลาไม่สมจริง | ไม่ได้เลือกอุปกรณ์ | ตั้ง part ใน Environment Settings |
| ไม่พบ part ที่ต้องการ | รุ่นของ PS ไม่รองรับ | ใช้การสังเคราะห์แบบ generic หรือส่งเน็ตลิสต์ VHDL/Verilog — ดูหัวข้อ 2.3.4 |
| โปรเจกต์สังเคราะห์ไม่ซ้ำผลเดิม | ไม่ได้บันทึกค่าคอนฟิก | ใช้ `File > Save Command File` แล้วรันสคริปต์ |
| สังเคราะห์ช้าผิดปกติ | เปิด effort สูง หรือเปิด Retiming | ลด effort หรือปิด Retiming (แต่ต้องใช้ค่าเดียวกันทุกรอบที่เปรียบเทียบ) |

## 6.4 ปัญหาระดับการส่งต่อและ Place & Route

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| Vivado อ่าน EDIF ไม่ได้ | ชื่อเซลล์/ไลบรารีไม่ตรงกับอุปกรณ์ | ตรวจว่า PS ใช้ไลบรารีของอุปกรณ์ถูกตัว; ถ้าไม่ได้ให้ใช้ทางสำรองในหัวข้อ 4.7 |
| พอร์ตไม่ถูกผูกกับพิน | ไม่ได้ใส่ XDC | เพิ่ม `nexys_a7_100t.xdc` |
| พอร์ตถูกผูกกับพินแต่ผิดพิน | ชื่อพอร์ตไม่ตรงกับ XDC | ตรวจชื่อพอร์ตใน RTL ให้ตรงกับ XDC ทุกตัวอักษร |
| Setup ไม่ผ่านหลัง route | เวลาเดินสายจริงมากกว่าที่ประมาณไว้ | ปรับ RTL, เพิ่ม effort, ใช้ phys_opt — ดูหัวข้อ 4.4.3 |
| Hold ไม่ผ่าน | เส้นทางสั้นเกินไปหลังเดินสาย | `phys_opt_design` หรือใส่ delay buffer — ดูหัวข้อ 4.5 |
| DRC error | ข้อกำหนดพินขัดแย้งกัน | ตรวจรายงาน DRC ว่าพินใดชนกัน |
| Unconstrained paths > 0 | พอร์ตบางตัวไม่ได้จำกัดเวลา | เติมเงื่อนไขใน XDC |
| Bitstream ที่ได้โปรแกรมไม่ขึ้น | ไฟล์ .bit ไม่ตรงกับบอร์ด หรือไม่ได้ตั้ง part | ตรวจ `xc7a100tcsg324-1` และความถี่โปรแกรมเมอร์ |
| บอร์ดแสดงผลผิด | RTL ผิด หรือสังเคราะห์จาก RTL คนละชุด | ตรวจว่าไฟล์ที่ใช้สร้าง bitstream ตรงกับที่ทดสอบ |

## 6.5 ปัญหาการเปรียบเทียบ QoR (บทที่ 5)

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| ผลของสองรอบเหมือนกันเป๊ะ | ลืมแก้ `sdc_file` ในสคริปต์ หรือสคริปต์ทั้งสองชี้ไฟล์เดียวกัน | ตรวจไฟล์ SDC ที่แต่ละรอบอ้างอิง |
| ทั้งสองรอบมี unconstrained paths | SDC ไม่ครบ | ห้ามเริ่มทดลองจนกว่าจะเป็น 0 |
| ประเมินผิดรอบ | ใช้ XDC 8 ns กับเน็ตลิสต์รอบ A | ยืนยันว่า XDC เป็น 10 ns ทั้งสองรอบ |
| post-route แย่กว่า pre-route มาก | เงื่อนไขการประเมินไม่เหมือนกับตอนสังเคราะห์ | ตรวจ input/output delay และ `set_false_path` |
| ผลต่างเล็กจนสรุปไม่ได้ | ดีไซน์เล็กเกินไป | เพิ่ม `int8_mac` หรือใช้โปรเจกต์จริง |
| สังเคราะห์รอบ 8 ns ใช้เวลานานมาก | effort สูง + เป้าหมายเข้ม | ลด effort (ใช้ค่าเดียวกันทั้งสองรอบ) |

## 6.6 รายการตรวจสอบก่อนส่งงาน (checklist)

### 6.6.1 ก่อนเริ่มสังเคราะห์

- [ ] RTL ผ่าน testbench แบบตรวจตัวเองทุกตัว
- [ ] testbench ครอบคลุมทุกโหมดของตัวออกแบบ
- [ ] เลือก part ตรงกับชิปจริงแล้ว
- [ ] ใส่ SDC ครบ: นาฬิกา, input delay, output delay, false path
- [ ] Compile ผ่านโดยไม่มี error/warning ที่ไม่เข้าใจ

### 6.6.2 หลังสังเคราะห์

- [ ] จำนวนเส้นทางที่ไม่ถูกจำกัด = 0
- [ ] setup slack วิกฤต ≥ 0
- [ ] ตรวจ utilization แล้วเทียบกับข้อจำกัดของชิป
- [ ] ระบุชนิดเซลล์หลักที่ใช้ (LUT / carry / DSP / BRAM)
- [ ] ตรวจว่าเส้นทางวิกฤตมาจากโค้ดส่วนที่คาด (ย้อนกลับได้)
- [ ] บันทึกตัวเลขลงตาราง QoR

### 6.6.3 ก่อนส่งต่อ Vivado

- [ ] ส่งออก EDIF แล้ว
- [ ] ตรวจว่า XDC มีพินครบทุกพอร์ตของ top
- [ ] ยืนยันว่า XDC ใช้คาบเวลาตามข้อกำหนดจริงของฮาร์ดแวร์
- [ ] เก็บ RTL ไว้ในโปรเจกต์ Vivado เพื่อการ debug
- [ ] ตรวจว่า part ใน Vivado ตรงกับ PS

### 6.6.4 ก่อนสร้าง bitstream

- [ ] setup WNS ≥ 0 และ TNS = 0
- [ ] hold WNS ≥ 0 และ TNS = 0
- [ ] unconstrained paths = 0
- [ ] DRC error = 0
- [ ] ไม่มี critical warning ว่าพอร์ตไม่ถูกจำกัด
- [ ] เกณฑ์ sign-off ผ่านจากสคริปต์

### 6.6.5 หลังทดสอบบนบอร์ด

- [ ] โปรแกรม bitstream แล้วบอร์ดทำงาน
- [ ] ทดสอบทุกแถวในตารางหัวข้อ 4.6.2
- [ ] ผลบนบอร์ดตรงกับผลจากการจำลอง
- [ ] บันทึกผลการทดสอบลงรายงาน

## 6.7 แบบฝึกหัดบทที่ 6

### Lab 6.1 — สร้างคลังปัญหาของทีม

1. รวบรวมปัญหาที่เจอระหว่างทำแล็บ 1–5 (ทั้งที่แก้เองได้และที่ไม่ได้)
2. สำหรับแต่ละปัญหา ให้เขียน: อาการ → สาเหตุ → วิธีแก้ → วิธีตรวจสอบว่าแก้แล้ว
3. เพิ่มรายการใหม่ที่พบในหัวข้อ 6.2–6.5 เข้าไปด้วย

**เกณฑ์ผ่าน**: มีคลังปัญหาอย่างน้อย 8 รายการ ในรูปแบบที่ทีมอ่านแล้วใช้ได้ทันที

### Lab 6.2 — ตรวจความพร้อมก่อนส่งงานจริง

1. ทำแบบฝึกหัด 1–5 อีกครั้งโดยไม่เปิด checklist
2. จากนั้นทำซ้ำโดยเปิด checklist และเทียบว่าพลาดจุดไหน
3. บันทึกว่าจุดที่พลาดบ่อยที่สุดคืออะไร

**เกณฑ์ผ่าน**: รอบที่สองพลาดน้อยกว่า และเข้าใจว่าจุดที่พลาดบ่อยคืออะไร

### Lab 6.3 — ทำให้เกณฑ์ sign-off ทำงานได้จริง

1. จงให้เกณฑ์ใน `check_signoff.tcl` ล้มเหลวจริง ๆ อย่างน้อย 2 กรณี (setup, hold, DRC, unconstrained)
2. ตรวจว่าสคริปต์รายงานเหตุผลที่ถูกต้อง และไม่สร้าง bitstream
3. บันทึกข้อความจริงที่ได้ (ไม่ใช่ที่คัดมา)

**เกณฑ์ผ่าน**: เกณฑ์ทำงานถูกต้องในทุกกรณี

## 6.8 สรุปบท

- ปัญหาเกือบทั้งหมดในงานสังเคราะห์อยู่ที่ขั้นก่อนหน้าเสมอ จึงควรไล่จากต้นทาง
- รายการตรวจสอบที่เขียนไว้ล่วงหน้า ช่วยลดเวลาที่ใช้แก้ปัญหาได้มากกว่าการจำจากหัว
- เกณฑ์ sign-off ที่ทำเป็นสคริปต์ ทำให้ "การตรวจก่อนปล่อย" เป็นกระบวนการมาตรฐาน
- คลังปัญหาของทีมเป็นทรัพย์สินที่ต้องสะสม เพราะปัญหาเดิมมักกลับมาในโปรเจกต์ถัดไป

**ขั้นตอนถัดไป**: ปิดท้ายการอบรมด้วยการทบทวนบทที่ 1–5 และส่งรายงานผลการทดลอง
พร้อมตารางบันทึกผล QoR ที่กรอกครบทุกช่อง
