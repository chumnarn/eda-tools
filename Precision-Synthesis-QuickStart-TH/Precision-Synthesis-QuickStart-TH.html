0.1 Precision Synthesis คืออะไร

Siemens Precision Synthesis (PS) คือเครื่องมือสังเคราะห์ตรรกะระดับอุตสาหกรรมที่ทำงานในสองบทบาทเดียวกัน

  1. ตัวสังเคราะห์ RTL (RTL Synthesis) — รับ RTL (VHDL/Verilog) แล้วแปลงเป็นเน็ตลิสต์

พร้อมประเมินเวลาและพื้นที่โดยใช้ไลบรารีเซลล์จริงของอุปกรณ์เป้าหมาย

  1. ตัวเชื่อมโยงระหว่างเครื่องมือ (Cross-tool Platform) — เป็นฐานข้อมูลกลางของทั้งระบบ

จุดยืนของบทนี้: ตามคู่มือ PS2018.1 ขั้นที่ 1b ("Add design source files") คือการนำ RTL เข้าโปรเจกต์ การสังเคราะห์จะไม่มีความหมายเลยถ้า RTL ยังไม่ผ่านการตรวจ บทนี้จึงใช้เวลากับคุณภาพของ RTL ก่อนแตะเครื่องมือสังเคราะห์

1.1 หลักการเขียน RTL ที่ Precision Synthesis รองรับ

1.1.1 มาตรฐานภาษา

Precision Synthesis รองรับ VHDL-93, VHDL-2002 และ VHDL-2008 และใช้แพ็กเกจมาตรฐาน ieee.std_logic_1164 กับ ieee.numeric_std

ข้อควรระวังรายละเอียด
ระบุมาตรฐานในไฟล์เพิ่ม library ieee; และ use ieee.std_logic_1164.all; use ieee.numeric_std.all;
ไม่ใช้ std_logic_arithแพ็กเกจนี้เป็นของ Synopsafe และมีพฤติกรรมกับ signed/unsigned กำกวม ให้ใช้ numeric_std แทน
ตั้งชื่อไฟล์ให้สื่อความหมายเช่น alu8.vhd, top_alu8.vhd

1.1.2 สิ่งที่ทำได้และไม่ควรทำ

ทำได้ไม่ควรทำ (สังเคราะห์ไม่ผ่านหรือผลลัพธ์เพี้ยน)
process (all) พร้อมกำหนดค่าเริ่มต้นให้ครบทุกเอาต์พุตใช้ wait/after ในโค้ดที่สังเคราะห์
ฟังก์ชันคงที่ที่คำนวณค่าตอนเอลาโบเรต เช่น clog2ใช้ตัวแปรที่ไม่ใช่ค่าคงที่เป็นความยาวบิต
numeric_std เต็มรูปแบบใช้ '+' ระหว่าง signed กับ integer โดยไม่แปลงชนิด
generate และ for generateใช้ real, time ในตรรกะเชิงวิเคราะห์
shared variable ไม่แนะนำใช้ shared variable (PS รองรับบางกรณีแต่ตรวจสอบยาก)

1.1.3 กฎข้อที่ 1 — ไม่ให้เกิด latch

ใน VHDL ถ้า signal ถูก assign ใน process แล้วไม่ได้ assign ทุก branch จะกลายเป็น latch ซึ่ง Precision จะสังเคราะห์ออกมาได้ แต่ผลลัพธ์ที่ได้มักไม่ตรงกับความคาดหมาย

-- ผิด: ไม่ได้กำหนดค่าให้ y ในทุกกรณี
process (op)
begin
  if op = "000" then
    y <= a + b;
  end if;
end process;

-- ถูก: กำหนดค่าเริ่มต้นก่อน แล้วค่อยแก้เฉพาะกรณีที่ต้องการ
process (all)
  variable y_v : signed(W-1 downto 0);
begin
  y_v := (others => '0');
  case op is
    when "000" => y_v := a + b;
    when "001" => y_v := a - b;
    when others => y_v := (others => '0');
  end case;
  y <= y_v;
end process;
ในโค้ดของคู่มือนี้ใช้รูปแบบที่สองทั้งหมด เพื่อให้ผลของการสังเคราะห์ตรงกับผลของการจำลองเสมอ

1.1.4 กฎข้อที่ 2 — process ที่ไวต่อนาฬิกาต้องมี rising_edge(clk) เสมอ

นี่คือบั๊กที่พบจริงระหว่างทำแล็บนี้ และเป็นบั๊กที่ทำให้ผลจำลองกับผลสังเคราะห์ คนละกันอย่างเงียบ ๆ ซึ่งเป็นอันตรายที่สุด

-- ผิด: process จะทำงานทั้งขอบขึ้นและขอบลง
--       ตัวชี้จึงเดินสองครั้งต่อหนึ่งรอบนาฬิกา
process (clk, rst_n)
begin
  if rst_n = '0' then
    cnt <= (others => '0');
  else
    cnt <= cnt + 1;
  end if;
end process;

-- ถูก
process (clk, rst_n)
begin
  if rst_n = '0' then
    cnt <= (others => '0');
  elsif rising_edge(clk) then
    cnt <= cnt + 1;
  end if;
end process;

อาการที่พบ: FIFO ขนาด 8 ช่อง "เต็ม" หลังเขียนเพียง 4 ค่า และตัวสะสม INT8 MAC ให้ผลเป็น สองเท่า ของที่ถูกต้อง การจำลองด้วย testbench ที่ไม่ตรวจกรณีนี้จะผ่านทั้งที่การทดสอบบนฮาร์ดแวร์จะพัง

ให้เพิ่มการตรวจ "นับรอบนาฬิกาจริง" ลงใน testbench เสมอ เช่น ตรวจว่าตัวนับเพิ่มขึ้น 1 ในทุกรอบ

1.1.5 กฎข้อที่ 3 — ระวังเรื่องการต่อสัญญาณ

ใน VHDL การต่อสัญญาณ A & B หมายถึง A อยู่บิตสูงกว่า B ซึ่งตรงข้ามกับความเข้าใจทั่วไปของคนที่มาจาก Verilog

-- ต้องการให้ SW[7:0] = a และ SW[15:8] = b
-- ต้องเขียน b ก่อนแล้วค่อย a
sw <= std_logic_vector(byte_of(b) & byte_of(a));

บั๊กนี้ทำให้ผลบวกถูก (เพราะสลับตัวก็ได้ผลเท่ากัน) แต่ผลลบผิด ทำให้ testbench ที่ทดสอบเฉพาะคำสั่ง ADD จะผ่านทั้งที่โค้ดผิด

เคสในคู่มือนี้: tb_top_alu8.vhd ใช้การทดสอบทุกคำสั่ง จึงจับบั๊กนี้ได้ สอนให้ผู้เรียนใช้ ตารางคำสั่งที่ครอบคลุมทุกโหมด ไม่ใช่แค่โหมดเดียว

1.3.2 แบบจำลองอ้างอิงที่ "คนละวิธี"

ในคู่มือนี้ RTL ใช้ numeric_std บนสัญญาณแบบ signed แต่แบบจำลองอ้างอิงใน tb/alu_ref_pkg.vhd ใช้ เลขจำนวนเต็ม (integer) ซึ่งเป็น arithmetic อิสระจาก RTL

-- ในแพ็กเกจอ้างอิง
procedure ref_alu(a_i, b_i : integer; op_i : std_logic_vector(2 downto 0);
                   y_o : out std_logic_vector(7 downto 0);
                   ovf_o : out std_logic; zero_o : out std_logic);

-- แบบจำลองการบวก: คำนวณก่อนตัดที่ 8 บิต จึงเห็น overflow ได้
when "000" =>
  full := a_i + b_i;
  if (full > 127) or (full < -128) then
    ovf_o := '1';
  end if;
  y_o := byte_of(full);

ข้อดีของการคำนวณก่อนตัด: เมื่อผลลัพธ์เต็ม 8 บิตทั้งที่ยังไม่เกินช่วง ค่าจริงยังถูกต้อง แต่เมื่อเกินช่วงจะเห็นได้ทันที

1.3.3 ข้อจำกัดของภาษา VHDL ที่พบจริง

ข้อควรรู้ 1 — อักษรไทยใช้ใน string literal ไม่ได้

-- ผิด: GHDL และ ModelSim จะรายงานว่า
--       "invalid character not allowed, even in a string"
report "ผิดพลาด: a=" & integer'image(a_v);

-- ถูก: ใช้ภาษาอังกฤษในข้อความ แล้วใส่คำอธิบายไทยไว้ใน comment
report "MISMATCH y: a=" & integer'image(a_v);

คำอธิบายภาษาไทยใน comment ไม่มีปัญหา เพราะ comment ไม่ได้อยู่ในข้อกำหนดของภาษา

ข้อควรรู้ 2 — others ใช้ใน expression ไม่ได้

-- ผิด: "others' choice not allowed for an aggregate in this context"
if y_v = (others => '0') then

-- ถูก: ใช้ constant
constant ZERO_VAL : signed(W-1 downto 0) := (others => '0');
if y_v = ZERO_VAL then

ข้อควรรู้ 3 — การสุ่มต้องทำซ้ำได้

ใช้ LFSR (linear feedback shift register) แทนฟังก์ชันสุ่มของระบบ เพื่อให้ผลการทดสอบเหมือนเดิมทุกครั้ง และเก็บ seed ไว้ในรายงาน

3.1 สร้างความเข้าใจเรื่อง slack ก่อน

3.1.1 slack คืออะไร

slack คือเวลาที่ "เหลือ" หลังจากทุกอย่างเสร็จ

คาบเวลานาฬิกา (period)      = 10.000 ns
- เวลาที่ต้องใช้ในเส้นทาง     =  8.200 ns
------------------------------------
= slack                      = +1.800 ns   ← ผ่าน มีเวลาเหลือ

คาบเวลานาฬิกา (period)      = 10.000 ns
- เวลาที่ต้องใช้ในเส้นทาง     = 11.400 ns
------------------------------------
= slack                      = -1.400 ns   ← ไม่ผ่าน เกินไป 1.4 ns

3.1.3 WNS และ TNS

ตัวชี้วัดความหมายใช้ทำอะไร

proc worst_slack {dt} {
    set paths [get_timing_paths -delay_type $dt -max_paths 1 -nworst 1]
    if {[llength $paths] == 0} { return "NA" }
    return [get_property SLACK [lindex $paths 0]]
}

set hold_slack  [worst_slack min]

set n_drc_error [regexp -count -nocase {ERROR} $drc_text]

4.4.3 การตีความเมื่อไม่ผ่าน

อาการสาเหตุที่เป็นไปได้ทางแก้

บทเรียนสำคัญ: งานที่ผ่านทุกเกณฑ์หลัง route มักจะผ่านได้ แต่งานที่ "ผ่าน" หลังสังเคราะห์อย่างเดียว อาจพังตอน route เพราะ ความหน่วงการเดินสายจริงอาจมากกว่าที่คาดไว้หลายเท่า

  เลือก "Hold" / delay_type = min

4.5.2 วิธีแก้ตามลำดับที่เหมาะสม

  1. ให้ Vivado แก้เองก่อน — phys_opt_design มีกลไกจัดการ hold อัตโนมัติ
  2. ปรับ directive

  1. ใส่ delay buffer เอง — เพิ่มเซลล์หน่วงในเส้นทางที่สั้นเกินไป

4.6.2 วิธีทดสอบบน Nexys A7-100T

ทดสอบวิธีทำผลที่คาดหวัง
นาฬิกาดูจอ 7 ส่วนเปลี่ยนไปเรื่อย ๆเปลี่ยนประมาณ 1,526 ครั้งต่อวินาที (100 MHz ÷ 2¹⁶)
ตัวคำนวณตั้ง SW[7:0] = 5, SW[15:8] = 3, BTN = ADDLED[7:0] แสดง 8 (0x08) บนจอแสดง "08"
ลบBTN = SUBLED[7:0] แสดง 2 (0x02)
zeroตั้ง operand เป็น 0LED[8] ติด
overflowตั้ง 127 + 1LED[9] ติด และผลเป็น 0x80
รีเซ็ตกดปุ่ม CPU RESET (C12)LED และจอถูกล้างเป็นศูนย์

4.6.3 วิธีตรวจว่าความถี่จอถูกต้อง

จอเปลี่ยนทุก 2¹⁶ รอบนาฬิกา = 100,000,000 ÷ 65,536 ≈ 1,526 ครั้งต่อวินาที ถ้าตาไม่จับได้แม้แต่กะพริบ แสดงว่าตัวนับหรือนาฬิกามีปัญหา — ให้ตรวจรายงาน timing ของเส้นทางนั้น

4.7 แนวทางสำรองเมื่อ EDIF ใช้ไม่ได้

อาจพบปัญหาที่ Vivado อ่าน EDIF ที่ส่งมาจาก PS ไม่ได้ เนื่องจากปัญหาเรื่องชื่อเซลล์ หรือไลบรารี มีแนวทางสำรอง 3 ทาง เรียงตามลำดับความสะดวก

ทางวิธีข้อดี/ข้อเสีย
1ให้ PS ส่งเน็ตลิสต์เป็น VHDL/Verilog แล้วให้ Vivado อ่านเป็น sourceง่าย แต่เสียข้อได้เปรียบของการใช้ไลบรารีอุปกรณ์ใน PS
2เก็บ RTL ไว้ในโปรเจกต์ Vivado แล้วให้ Vivado สังเคราะห์เองได้ debug ง่าย แต่ไม่ได้ทดสอบคุณภาพของเน็ตลิสต์จาก PS
3ตรวจไลบรารีที่ PS ใช้ แล้วจัดการให้ถูกต้องแก้ที่ต้นเหตุ แต่ต้องเข้าใจรูปแบบ EDIF ของอุปกรณ์
คำแนะนำสำหรับการอบรม: ให้ทำแบบทาง 2 ควบคู่กับทาง 1 เสมอ เพราะผลลัพธ์ของบทที่ 5 (เปรียบเทียบ 10 ns กับ 8 ns) ต้องเปรียบเทียบ เน็ตลิสต์ที่สังเคราะห์ด้วยเป้าหมายต่างกัน ถ้าให้ Vivado สังเคราะห์ใหม่ทั้งคู่ ก็จะไม่ได้ทดสอบสิ่งที่ต้องการทดสอบจริง

บทที่ 5 — ทดลองเปรียบเทียบ QoR: เป้าหมายสังเคราะห์ 10 ns กับ 8 ns

เป้าหมายของบทนี้: ให้ผู้เรียนพิสูจน์ด้วยตัวเองว่า "ยิ่งบีบเวลาให้เข้ม ยิ่งได้ผลดีขึ้น" เป็นความเข้าใจผิด และรู้ว่าการประเมิน QoR ที่ถูกต้อง ต้องประเมิน หลัง routing ด้วย เงื่อนไขของบอร์ดจริง เสมอ ไม่ใช่เงื่อนไขที่ตั้งไว้ตอนสังเคราะห์

5.1 ปัญหาที่กำลังศึกษา

บอร์ด Nexys A7-100T มีนาฬิกาหลัก 100 MHz คือคาบเวลา 10 ns

สมมติว่าทีมงานต้องการ "ประกันความเร็ว" มากกว่านั้น จึงตั้งเป้าหมายสังเคราะห์เป็น 8 ns (คิดเป็น 125 MHz) โดยตั้งสมมติฐานว่า "ยิ่งบีบเวลา ยิ่งได้ดีไซน์ที่เร็วกว่าและปลอดภัยกว่า"

คำถามของการทดลองนี้คือ: สมมติฐานนั้นจริงหรือไม่ เมื่อวัดจากผลจริงหลังเดินสาย?

5.2 ทฤษฎี: การบีบเวลาทำอะไรกับตัวสังเคราะห์

5.2.1 สิ่งที่ตัวสังเคราะห์ทำเมื่อเป้าหมายเข้มขึ้น

เมื่อบีบเวลาที่ต้องการ ตัวสังเคราะห์จะพยายามลดความหน่วงของเส้นทางวิกฤตด้วยวิธีต่อไปนี้ เรียงตามลำดับที่มักถูกใช้

#วิธีผลต่อเวลาผลต่อพื้นที่ผลข้างเคียง
1เปลี่ยนโครงสร้างตรรกะให้สั้นลงดีขึ้นมากเพิ่มขึ้นตรรกะซับซ้อนขึ้น อาจเพิ่มพื้นที่มาก
2ทำซ้ำ (duplicate) ตรรกะที่ใช้ร่วมกันดีขึ้นเพิ่มขึ้นโครงสร้างฟิสิกส์เปลี่ยน ต้องวางวางใหม่
3ใส่รีจิสเตอร์เพิ่ม (pipeline)ดีขึ้นมากเพิ่มขึ้นมากเปลี่ยนสมมติฐานของเส้นทาง I/O ต้องแก้ SDC
4ย้ายรีจิสเตอร์ (retiming)ดีขึ้นเพิ่ม/ลดเล็กน้อยเปลี่ยนโครงสร้างขอบเขตรีจิสเตอร์
5เปลี่ยนตัวเลือกของการแมปเซลล์ดีขึ้นเล็กน้อยเพิ่มเล็กน้อยต้องเลือกเซลล์ที่วางวางยากขึ้น

5.2.3 กรณีที่การบีบเวลา "ถูกต้อง"

การบีบเวลาไม่ได้ผิดเสมอไป มีกรณีที่เหมาะสม

กรณีเหตุผล
บอร์ดมีนาฬิกาเร็วกว่านี้จริงต้องการประสิทธิภาพที่ 125 MHz จริง ๆ
ต้องการ headroom สำหรับอุณหภูมิ/แรงดันที่แตกต่างกันเผื่อ margin ไว้
ยังไม่รู้ความถี่ปลายทางตั้งค่าขั้นต่ำไว้ก่อนเพื่อคุ้มค่า
การทำงานแบบ timing closureต้องการให้ตัวสังเคราะห์ทำงานหนักขึ้น

แต่ในกรณีของบอร์ด Nexys A7-100T ที่มีนาฬิกา 100 MHz การตั้ง 8 ns ไม่ใช่ข้อกำหนดของฮาร์ดแวร์ เป็นการตั้งที่ "เข้มกว่าที่จำเป็น" ซึ่งเป็นหัวข้อของการทดลองนี้

ถ้า Retiming ทำให้รีจิสเตอร์ขยับข้ามพอร์ต I/O สมมติฐานของ SDC จะไม่ตรงอีกต่อไป สังเกตได้จากรายงานของ PS ที่ Startpoint/Endpoint ของเส้นทางเปลี่ยนไป

วิธีแก้

  1. ปิด Retiming แล้วสังเคราะห์ซ้ำทั้งสองรอบ (ทางเลือกที่ปลอดภัย)
  2. หรือยอมรับการเปลี่ยนแปลงและปรับ SDC ให้ตรงกับโครงสร้างใหม่
ข้อสังเกตนี้เป็นตัวอย่างที่ดีของหลัก "การเปลี่ยนสมมติฐานของเส้นทาง I/O ต้องไปพร้อมกับการเปลี่ยนเงื่อนไข"

5.6.4 ปัญหา: ผลต่างของสองรอบน้อยเกินไปจนสรุปไม่ได้

โปรเจกต์ตัวอย่างนี้เล็กมาก (ประมาณ 150 LUT) ผลของการบีบเวลาจึงมีผลน้อย วิธีเพิ่มความชัดเจนของการทดลอง

  • เพิ่ม int8_mac.vhd เข้าไป ซึ่งมีตัวคูณและ pipeline ที่ซับซ้อนกว่า
  • เพิ่มกรณีขยาย ให้มีตัวคูณหลายตัวและเส้นทางยาวขึ้น
  • ใช้โปรเจกต์จริงของทีมแทน

บทที่ 6 — แนวทางแก้ปัญหาและรายการตรวจสอบ

บทนี้เป็นคลังปัญหาจริงที่พบระหว่างทำแล็บในคู่มือนี้ รวมถึงรายการตรวจสอบ ที่ใช้ก่อน–หลังแต่ละขั้น ควรใช้เป็น "แผนกู้เมื่อติด" ในห้องเรียน

6.1 แนวทางวิเคราะห์ปัญหาแบบเป็นขั้นตอน

เมื่อมีปัญหา ให้ไล่จากข้างต้น (ต้นทาง) ไปปลายทางตามลำดับนี้ เพราะปัญหาเกือบทั้งหมดในงานสังเคราะห์จะอยู่ที่ขั้นตอนก่อนหน้าเสมอ

1. RTL ถูกต้องไหม?          → ผ่าน testbench แล้วหรือยัง
2. เงื่อนไขเวลาครบไหม?        → มีเส้นทาง unconstrained หรือไม่
3. ตัวสังเคราะห์ผิดไหม?      → เทียบ pre-route กับค่าที่คาด
4. การวางวาง/เดินสายผิดไหม? → เทียบ post-route กับ pre-route
5. ส่งต่อระหว่างเครื่องมือผิดไหม? → เช็ค EDIF / XDC
6. ข้อจำกัดของชิปเกินไหม?   → utilization

6.2 ปัญหาระดับ RTL และการจำลอง

อาการสาเหตุที่พบจริงวิธีแก้
ผลจำลองไม่ตรงกับผลสังเคราะห์process ที่ไวต่อ clk ขาด rising_edge(clk)เพิ่ม elsif rising_edge(clk) then — ดูหัวข้อ 1.1.4
ค่าผลลัพธ์เป็นสองเท่าที่ควรเป็นตัวสังเคราะห์/การจำลองทำงานทั้งขอบขึ้นและขอบลงตรวจทุก process ที่ sensitive กับ clk
ผลต่างกันเฉพาะคำสั่ง SUBสลับลำดับ operand เพราะ A & B เอา A ไว้บิตสูงสลับลำดับในการต่อสัญญาณ — ดูหัวข้อ 1.1.5
ค่า overflow ไม่ตรงส่งค่า byte ดิบเข้าแบบจำลองที่ตีความแบบมีเครื่องหมายแปลงด้วย int_of(byte_of(x)) ก่อนส่งเข้าแบบจำลอง
เกิด latch ในการจำลองไม่ได้กำหนดค่าเริ่มต้นให้ทุกเอาต์พุตใส่ค่าเริ่มต้นก่อน case
ไฟล์ VHDL คอมไพล์ไม่ผ่านมีอักษรไทยใน string literalใช้ภาษาอังกฤษในข้อความ report — ดูหัวข้อ 1.3.3
คอมไพล์ไม่ผ่าน "'others' choice not allowed"ใช้ (others => '0') ใน expressionใช้ constant — ดูหัวข้อ 1.3.3
GHDL ขึ้น "invalid character not allowed"พาธที่มีอักษรไทยคัดลอกไปพาธ ASCII — ดูหัวข้อ 0.3.3
handshake ตรวจผิดที่อ่านค่า signal หลังขอบขึ้น (post-edge) แทนก่อนขอบขึ้นใช้ process ที่ sensitive กับ clk และอ่านค่าในนั้น
testbench ไม่จบไม่มีการเรียก stop/finishเพิ่ม stop เมื่อผ่าน และ assert false severity failure เมื่อไม่ผ่าน

6.3 ปัญหาระดับโปรเจกต์ Precision

อาการสาเหตุวิธีแก้
Unable to find entityเพิ่มไฟล์มาผิดลำดับลบออกแล้วเพิ่มใหม่ โดยเริ่มจาก leaf module
hierarchy ไม่ครบโมดูลในไฟล์เดียวกันไม่ถูกอ่านแยกแต่ละ entity ออกเป็นไฟล์ย่อย หรือตรวจรูปแบบไฟล์
ไม่มีรายงานเวลาเลยยังไม่ได้ใส่ SDC หรือไม่ได้กำหนดความถี่ทำหัวข้อ 2.4
รายงานเวลาเป็นศูนย์/ว่างไม่มี clock ที่เกี่ยวข้องตรวจ create_clock และชื่อพอร์ต
เส้นทางไม่ถูกจำกัดจำนวนมากลืม set_input_delay / set_output_delayดูตารางในหัวข้อ 3.4.3

โปรเจกต์สังเคราะห์ไม่ซ้ำผลเดิมไม่ได้บันทึกค่าคอนฟิกใช้ File > Save Command File แล้วรันสคริปต์

6.4 ปัญหาระดับการส่งต่อและ Place & Route

อาการสาเหตุวิธีแก้
Vivado อ่าน EDIF ไม่ได้ชื่อเซลล์/ไลบรารีไม่ตรงกับอุปกรณ์ตรวจว่า PS ใช้ไลบรารีของอุปกรณ์ถูกตัว; ถ้าไม่ได้ให้ใช้ทางสำรองในหัวข้อ 4.7

6.5 ปัญหาการเปรียบเทียบ QoR (บทที่ 5)

อาการสาเหตุวิธีแก้
ผลของสองรอบเหมือนกันเป๊ะลืมแก้ sdc_file ในสคริปต์ หรือสคริปต์ทั้งสองชี้ไฟล์เดียวกันตรวจไฟล์ SDC ที่แต่ละรอบอ้างอิง
ทั้งสองรอบมี unconstrained pathsSDC ไม่ครบห้ามเริ่มทดลองจนกว่าจะเป็น 0
ประเมินผิดรอบใช้ XDC 8 ns กับเน็ตลิสต์รอบ Aยืนยันว่า XDC เป็น 10 ns ทั้งสองรอบ
post-route แย่กว่า pre-route มากเงื่อนไขการประเมินไม่เหมือนกับตอนสังเคราะห์ตรวจ input/output delay และ set_false_path

  • รายการตรวจสอบที่เขียนไว้ล่วงหน้า ช่วยลดเวลาที่ใช้แก้ปัญหาได้มากกว่าการจำจากหัว
  • เกณฑ์ sign-off ที่ทำเป็นสคริปต์ ทำให้ "การตรวจก่อนปล่อย" เป็นกระบวนการมาตรฐาน
  • คลังปัญหาของทีมเป็นทรัพย์สินที่ต้องสะสม เพราะปัญหาเดิมมักกลับมาในโปรเจกต์ถัดไป

ขั้นตอนถัดไป: ปิดท้ายการอบรมด้วยการทบทวนบทที่ 1–5 และส่งรายงานผลการทดลอง พร้อมตารางบันทึกผล QoR ที่กรอกครบทุกช่อง

ก.4 สคริปต์เกณฑ์ sign-off ฉบับสมบูรณ์

# check_signoff.tcl
set min_setup_slack 0.0
set min_hold_slack  0.0
set max_drc_errors  0

proc worst_slack {dt} {
    set paths [get_timing_paths -delay_type $dt -max_paths 1 -nworst 1]
    if {[llength $paths] == 0} { return "NA" }
    return [get_property SLACK [lindex $paths 0]]
}

set setup_slack [worst_slack max]
set hold_slack  [worst_slack min]
set n_unconstrained [llength [get_timing_paths -unconstrained -nworst 100]]
set n_drc_error [regexp -count -nocase {ERROR} [report_drc -return_string]]

set signoff_ok 1
set reasons {}
if {$setup_slack eq "NA" || $setup_slack < $min_setup_slack} {
    lappend reasons "setup slack $setup_slack"; set signoff_ok 0 }
if {$hold_slack eq "NA" || $hold_slack < $min_hold_slack} {
    lappend reasons "hold slack $hold_slack"; set signoff_ok 0 }
if {$n_drc_error > $max_drc_errors} {
    lappend reasons "DRC errors $n_drc_error"; set signoff_ok 0 }
if {$n_unconstrained > 0} {
    lappend reasons "unconstrained paths $n_unconstrained"; set signoff_ok 0 }

set fh [open $out_dir/signoff_report.txt w]
puts $fh "setup slack (worst) : $setup_slack ns"
puts $fh "hold  slack (worst) : $hold_slack ns"
puts $fh "DRC errors          : $n_drc_error"
puts $fh "unconstrained paths : $n_unconstrained"
if {$signoff_ok} { puts $fh "RESULT: PASS" } else {
    puts $fh "RESULT: FAIL"
    foreach r $reasons { puts $fh "  - $r" } }
close $fh

ภาคผนวก ข — ประจำศัพท์ไทย–อังกฤษ (Glossary)

จัดเรียงตามลำดับตัวอักษรภาษาอังกฤษ ค้นหาได้ทั้งคำไทยและคำอังกฤษ

A

อังกฤษไทยคำอธิบาย
ASIC (Application-Specific Integrated Circuit)วงจรรวมเฉพาะกิจชิปที่ออกแบบมาเพื่องานเฉพาะทาง
Async resetรีเซ็ตแบบไม่ประสานเวลารีเซ็ตที่ทำงานโดยไม่ต้องรอขอบนาฬิกา
AXI-Stream—โปรโตคอลส่งข้อมูลแบบสตรีมมิ่งที่ใช้ tvalid/tready

B

อังกฤษไทยคำอธิบาย
Backpressureแรงดันย้อนกลับกลไกที่ผู้รับบอกผู้ส่งให้หยุดส่งชั่วคราว
Bitstreamบิตสตรีมไฟล์ที่เขียนลงชิป FPGA เพื่อกำหนดการทำงานของวงจร
Black boxกล่องดำโมดูลที่ทำงานถูกต้องแต่ไม่เห็นรายละเอียดภายใน
BRAM (Block RAM)—หน่วยความจำบล็อกภายใน FPGA

C

อังกฤษไทยคำอธิบาย
Clock skewความเบี่ยงเบนนาฬิกาความต่างของเวลาที่นาฬิกาไปถึงจุดต่าง ๆ ในวงจร
Congestionความแน่นบริเวณที่มีการเชื่อมต่อหนาแน่นเกินไป ทำให้เดินสายยาก
Critical pathเส้นทางวิกฤตเส้นทางที่ใช้เวลามากที่สุด กำหนดความเร็วของวงจร
Cross-probingการเชื่อมข้ามการคลิกที่วงจรแล้วเปิดโค้ดต้นทางทันที

D

อังกฤษไทยคำอธิบาย
DSP48E1—หน่วยคูณสะสมสำเร็จใน FPGA ของ Xilinx 7-Series
DRC (Design Rule Check)การตรวจกฎการออกแบบตรวจข้อผิดพลาดของข้อจำกัดทางกายภาพ
DFF/DREฟลิป-flopรีจิสเตอร์เก็บค่า 1 บิต

E

อังกฤษไทยคำอธิบาย
EDIF (Electronic Design Interchange Format)รูปแบบแลกเปลี่ยนข้อมูลอิเล็กทรอนิกส์มาตรฐานนำเน็ตลิสต์ของวงจร ใช้ส่งต่อระหว่างเครื่องมือ
Effort (optimization effort)ความพยายามในการปรับปรุงปริมาณเวลาและทรัพยากรที่เครื่องมือใช้ในการปรับปรุง
Elaborationการขยายตัวกระบวนการสร้าง hierarchy และตรวจการเชื่อมต่อของโมดูล

F

อังกฤษไทยคำอธิบาย
FIFO (First In First Out)—โครงสร้างข้อมูลแบบเข้าก่อนออกก่อน
Fix-upการแก้ให้ถูกต้องการแก้ไขปัญหาที่พบระหว่างกระบวนการ

G

อังกฤษไทยคำอธิบาย
Gate-level netlistเน็ตลิสต์ระดับประตูตรรกะเน็ตลิสต์ที่เซลล์ถูกแทนที่ด้วยประตูตรรกะพื้นฐาน
Gray codeรหัสเกรย์รหัสที่บิตที่เปลี่ยนมีเพียงหนึ่งบิตต่อการนับถัดไป

H

อังกฤษไทยคำอธิบาย
Hold slackสลักโฮลดเวลาสำรองของข้อกำหนดการถือข้อมูล (ต้องตรวจหลังเดินสาย)
Hold timeเวลาถือเวลาที่ข้อมูลต้องคงอยู่หลังขอบนาฬิกา

I

อังกฤษไทยคำอธิบาย
I/O delayเวลาหน่วงของอินพุต/เอาต์พุตเวลาที่สัญญาณใช้เวลาเดินทางถึง/ออกจากชิป
IP (Intellectual Property)ทรัพย์สินทางปัญญาโมดูลสำเร็จรูปที่ซื้อมาใช้ในดีไซน์

L

อังกฤษไทยคำอธิบาย
Latencyเวลาหน่วงเวลาที่ข้อมูลใช้เดินทางผ่านวงจร
LUT (Look-Up Table)ตารางค้นหาหน่วยตรรกะพื้นฐานของ FPGA ที่ทำหน้าที่เป็นตรรกะตามต้องการได้
LUTRAM—LUT ที่ถูกใช้เป็นหน่วยความจำขนาดเล็ก

M

อังกฤษไทยคำอธิบาย
Master clockนาฬิกาหลักนาฬิกาต้นทางที่กระจายไปทั่วทั้งชิป
Metastabilityเมตาสเทเบิลิตีสถานะกึ่งไม่เสถียรของ flip-flop เมื่อสัญญาณเปลี่ยนใกล้ขอบนาฬิกามาก ๆ
Multiplexer (mux)ตัวเลือกสัญญาณวงจรเลือกหนึ่งในหลายสัญญาณเข้าออก

N

อังกฤษไทยคำอธิบาย
Netlistเน็ตลิสต์รายการเซลล์และการเชื่อมต่อทั้งหมดของวงจรหลังสังเคราะห์
Next-pointจุดถัดไปจุดสัญญาณที่รับผลจากจุดปัจจุบัน

O

อังกฤษไทยคำอธิบาย
Open cell libraryไลบรารีเซลล์แบบเปิดไลบรารีที่เปิดเผยโครงสร้างภายในของเซลล์
Optimization effortความพยายามในการปรับปรุงดู Effort

P

อังกฤษไทยคำอธิบาย
Part (FPGA part)รุ่นชิประบุชนิดชิป ตระกูล แพ็กเกจ และคลาสความเร็ว
Phys_optการปรับปรุงระดับการจัดวางขั้นตอนปรับปรุงที่ทำหลังวางวางเพื่อแก้ปัญหาเวลา
Pipelineไปป์ไลน์แบ่งตรรกะเป็นหลายขั้นเพื่อลดความยาวของเส้นทาง
Placeการวางวางการกำหนดตำแหน่งเซลล์ในชิป
Place and Route (P&R)การวางวางและเดินสายขั้นตอนสร้างการจัดวางจริงของวงจร
Precision Synthesis (PS)—เครื่องมือสังเคราะห์ตรรกะของซีเมนส์
Propagation delayเวลาการเผยแพร่เวลาที่สัญญาณใช้เดินทางผ่านประตูตรรกะ

Q

อังกฤษไทยคำอธิบาย
QoR (Quality of Results)คุณภาพของผลลัพธ์ตัวชี้วัดคุณภาพของเน็ตลิสต์ ทั้งด้านเวลาและพื้นที่
Quasi-staticกึ่งคงที่ค่าที่คงที่ในช่วงเวลายาว ๆ แต่อาจเปลี่ยนได้ในอีกช่วงหนึ่ง

R

อังกฤษไทยคำอธิบาย
Registerรีจิสเตอร์วงจรเก็บค่า 1 บิต (flip-flop)
Retimingการย้ายรีจิสเตอร์เทคนิคที่ย้ายรีจิสเตอร์ข้ามตรรกะเพื่อปรับปรุงเวลา
Routeการเดินสายการกำหนดเส้นทางจริงของสัญญาณระหว่างเซลล์
Routing delayเวลาเดินสายเวลาที่สัญญาณใช้เดินทางบนสายที่วางจริง

S

อังกฤษไทยคำอธิบาย
Schematicแผนผังวงจรมุมมองของวงจรที่แสดงเป็นสัญลักษณ์ของเซลล์และการเชื่อมต่อ
SDC (Synopsys Design Constraints)—ภาษาสำหรับกำหนดเงื่อนไขเวลาและข้อจำกัดอื่น
Self-checking testbenchtestbench แบบตรวจตัวเองtestbench ที่ตรวจผลและตัดสินใจผ่าน/ไม่ผ่านเองได้
Setup slackสลักตั้งค่าเวลาสำรองของข้อกำหนดการตั้งค่าข้อมูล
Setup timeเวลาตั้งค่าเวลาที่ข้อมูลต้องมาถึงก่อนขอบนาฬิกา
Slackเวลาสำรองเวลาที่เหลือหลังจากความต้องการครบทุกอย่าง
Speed gradeคลาสความเร็วระดับความเร็วของซิลิกอนในอุปกรณ์
Synthesisการสังเคราะห์การแปลง RTL เป็นเน็ตลิสต์
Synchronous resetรีเซ็ตแบบประสานเวลารีเซ็ตที่ทำงานเมื่อมีขอบนาฬิกา

T

อังกฤษไทยคำอธิบาย
Tcl—ภาษาสคริปต์ที่ใช้ควบคุมเครื่องมือ EDA หลายตัว
Timing closureการปิดเวลากระบวนการปรับดีไซน์จนให้ผ่านข้อกำหนดเวลา
TNS (Total Negative Slack)ผลรวมสลักลบผลรวมของ slack ที่เป็นลบทั้งหมด
Typeชนิดข้อมูลเช่น std_logic, signed, unsigned

U

อังกฤษไทยคำอธิบาย

Utilizationการใช้ทรัพยากรสัดส่วนทรัพยากรของชิปที่ดีไซน์ใช้

V

อังกฤษไทยคำอธิบาย
VHDL—ภาษาอธิบายฮาร์ดแวร์ (Very High Speed Integrated Circuit Hardware Description Language)
Vivado—เครื่องมือของ AMD/Xilinx สำหรับสังเคราะห์ วางวาง เดินสาย และสร้าง bitstream

W

อังกฤษไทยคำอธิบาย
Waveformรูปคลื่นสัญญาณกราฟแสดงการเปลี่ยนแปลงของสัญญาณตามเวลา
WNS (Worst Negative Slack)สลักลบแย่ที่สุดslack ที่แย่ที่สุดของทุกเส้นทาง
