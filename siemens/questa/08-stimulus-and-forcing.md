## 1. สามวิธีให้ stimulus

| วิธี | ทำได้เมื่อ | เหมาะกับ |
|---|---|---|
| **เขียนในโค้ด testbench** | ตั้งแต่ต้น | การทดสอบปกติที่ต้องทำซ้ำได้ |
| **force / release จากบรรทัดคำสั่ง** | ระหว่างที่ simulation หยุด | การ debug แบบ interactive และการสำรวจ corner case |
| **Waveform Editor** | ระหว่างที่ simulation หยุด | การป้อน pattern ที่ซับซ้อน เช่น รูปแบบสัญญาณนาฬิกา |

> **หลักการสำคัญ:** stimulus ที่ใส่ด้วย `force` เป็นผลลัพธ์ของการ debug
> ไม่ใช่ส่วนหนึ่งของ testbench ที่ส่งมอบ
> เพราะ testbench ที่ดีต้องให้ผลเหมือนเดิมทุกครั้งที่รัน

## 2. `force`, `deposit` และ `apply`

| คำสั่ง | ผล | ต้องคืนค่าหรือไม่ |
|---|---|---|
| `force <วัตถุ> <ค่า>` | บังคับค่าถาวร จนกว่าจะ `release` | **ต้อง** `release` |
| `deposit <วัตถุ> <ค่า>` | ฝังค่าในเวลาปัจจุบันเท่านั้น รอบเวลาถัดไป driver เดิมกลับมาคุม | ไม่ต้อง |
| `apply <วัตถุ> <ค่า>` | ชื่อเดิมของ `deposit` ในรุ่นเก่า ไม่แนะนำให้ใช้ | ไม่ต้อง |

### 2.1 รูปแบบคำสั่ง

```text
force tb_counter_forced/en 1
force tb_x/bus 16'h1234
release tb_counter_forced/en
```

> **ห้ามลืม `release`** ค่าที่ force ไว้จะค้างไปตลอดการจำลอง
> ทำให้ผลการทดสอบครั้งหลังไม่ตรงกับครั้งแรก
> และทำให้การ debug ต่อไปสับสน เพราะค่าที่เห็นไม่ได้มาจากโค้ด

### 2.2 การเลือกฐานของค่าที่ force

ค่าที่ force ใส่เขียนด้วยรูปแบบของ Verilog ได้ เช่น `16'h1234` `8'b1010_1010`
หรือเขียนเป็นเลขฐานสิบได้เมื่อชนิดของสัญญาณเป็น integer

## 3. ทำไม `force` จึงมีผลต่อวงจรจริง

### 3.1 ใน VHDL สัญญาณหนึ่งตัวมี driver ได้หลายตัว

VHDL อนุญาตให้สัญญาณหนึ่งตัวถูกขับพร้อมกันได้หลายแหล่ง
เช่น ชนิด `std_logic` เป็นชนิดที่ *resolved* คือเมื่อมีหลาย driver
ผลลัพธ์จะถูกรวมด้วยกฎของตาราง truth

| ค่าจาก driver | ค่าจาก driver | ผลลัพธ์ของ `std_logic` |
|---|---|---|
| 0 | 0 | 0 |
| 1 | 1 | 1 |
| 0 | 1 | X |
| 0 | Z | 0 |
| 1 | Z | 1 |

> นี่คือเหตุผลที่ค่า `X` มักเกิดขึ้น
> ไม่ใช่เพราะบั๊ก แต่เพราะมีสอง driver ขับค่าขัดกัน

### 3.2 `force` ทำอะไรกับ driver

เมื่อสั่ง `force` สัญญาณนั้นจะถูกยกเลิกการควบคุมโดย driver ปกติ
และถูกบังคับให้มีค่าตามที่สั่ง
วงจรจริงจึงเห็นค่านั้นเหมือนกับว่าค่านั้นมาจาก driver จริง

เมื่อสั่ง `release` driver เดิมจะกลับมาคุมสัญญาณอีกครั้ง
และค่าจะเปลี่ยนกลับเป็นค่าที่โค้ดกำหนด

### 3.3 ผลกับการทำงานของ process

process ที่พยายามจะขับค่าใหม่ยังทำงานตามปกติ
แต่ผลลัพธ์จะถูกบังคับไว้ที่ค่าที่ `force` ไว้

> นี่ทำให้ `force` เป็นเครื่องมือที่ทรงพลังแต่ก็อันตราย
> เพราะจะทำให้โค้ดที่ถูกต้องแสดงผลผิด
> ใช้เฉพาะตอน debug และ `release` เสมอเมื่อเสร็จ

## 4. ตำแหน่งที่ต้อง `force` ใน VHDL

> **นี่คือจุดที่ผู้ย้ายจาก Verilog มักพลาดมากที่สุด**

### 4.1 กฎของ VHDL

เมื่อ instance ถูกผูกกับสัญญาณด้วย `port map` แบบ *association*
พอร์ตนั้น **ไม่ใช่ signal แยก** แต่เป็นชื่อแฝงของสัญญาณที่อยู่นอก

```vhdl
dut : entity work.counter_forced
  port map (
    en => en            -- พอร์ต "en" ของ DUT คือสัญญาณ tb_counter_forced/en
  );
```

ดังนั้นการ force ที่พอร์ตของ instance **ไม่มีผล**
ต้อง force ที่สัญญาณต้นทางที่ testbench ขับ

| คำสั่ง | ผล |
|---|---|
| `force tb_counter_forced/en 1` | **ถูกต้อง** — เป็นสัญญาณที่ testbench ขับ |
| `force tb_counter_forced/dut/en 1` | **ไม่มีผล** — เป็นพอร์ตที่ผูกกับสัญญาณอยู่แล้ว |

### 4.2 เทียบกับ Verilog

ใน Verilog พอร์ตของ instance เป็น signal แยก
จึง force ที่ `tb.dut.en` ได้ผล

| ภาษา | ตำแหน่งที่ force ได้ผล |
|---|---|
| Verilog | `tb.dut.en` (พอร์ตของ instance) |
| VHDL | `tb.en` (สัญญาณที่ประกาศใน testbench) |

### 4.3 วิธีหาตำแหน่งที่ถูกต้อง

1. คลิกขวาที่สัญญาณในหน้าต่าง Structure (sim)
2. เลือก **Drivers** จะเห็นว่าสัญญาณนั้นถูกขับโดยอะไร
3. หรือพิมพ์ `examine -hierarchical <สัญญาณ>` เพื่อดูทั้ง hierarchy

## 5. ตัวอย่างจริงจาก `ex02_force_release`

### 5.1 ตารางเวลาของตัวอย่าง

| เวลา | เหตุการณ์ |
|---|---|
| 5 ns | ขอบนาฬิกาที่ 1 — reset ทำงาน ตัวนับเป็น 0 |
| 15–45 ns | `en` เปิด ตัวนับนับถึง 4 |
| **46 ns** | `PHASE_FORCE_WINDOW start` — testbench ขับ `en` เป็น 0 |
| 55, 65, 75 ns | ขอบนาฬิกาในช่วงหยุด ตัวนับต้องคงค่า 4 |
| **76 ns** | `PHASE_FORCE_WINDOW end` |
| 85, 95 ns | `en` เปิดอีกครั้ง ตัวนับนับต่อเป็น 5 และ 6 |
| 96 ns | จบการทดสอบ |

เวลาเหล่านี้วัดได้จาก log ของการจำลองด้วย GHDL 1.0.0
ดูหลักฐานใน
[`reports/ex02_force_release_tb_counter_forced_run.log`](../../../code/reference/questa/reports/ex02_force_release_tb_counter_forced_run.log)

### 5.2 ขั้นตอนการทดลอง

รันแบบมี GUI

```bash
cd code/reference/questa/examples/ex02_force_release

vlib work
vmap work work
vcom -2008 -work work src/counter_forced.vhd
vcom -2008 -work work tb/tb_counter_forced.vhd
vsim -do "do ../../tcl/ex02_force_release.do" work.tb_counter_forced
```

ไฟล์ `.do` จะรันไปถึง **50 ns** แล้วหยุด
จากนั้นพิมพ์คำสั่งที่ prompt `VSIM>` ตามลำดับ

```text
force tb_counter_forced/en 1
run 20 ns
examine tb_counter_forced/cnt
release tb_counter_forced/en
run 20 ns
```

### 5.3 ผลที่ต้องเห็น

**หลัง `force` และ `run 20 ns`**

ตัวนับนับต่อจาก 4 เป็น 5 และ 6 ทั้งที่ testbench ขับ `en` เป็น 0
และ testbench จะรายงาน

```text
cnt mismatch: got 5 expected 4
```

> ข้อความ mismatch นี้ **คือหลักฐานว่า force มีผลจริง**
> ไม่ใช่บั๊ก — เพราะ testbench คาดว่าตัวนับจะคงค่า 4 ตอน `en` เป็น 0
> ถ้า force สำเร็จ ตัวนับจะนับต่อ จึงไม่ตรงกับที่คาด

**หลัง `release`**

สัญญาณ `en` กลับไปเป็น 0 ตามที่ testbench ขับ
และตัวนับหยุดนับในช่วงที่เหลือ

### 5.4 ทำไมต้องเป็นช่วงเวลาแบบนี้

การออกแบบให้มีข้อความ `PHASE_FORCE_WINDOW` กำกับไว้
มีเหตุผลสองข้อ

1. **ผู้เรียนรู้ว่าจะหยุดที่เวลาใด** โดยไม่ต้องนับเอง
2. **ผลที่ได้ทำซ้ำได้** ทุกคนได้ผลเหมือนกัน จึงเปรียบเทียบกันได้

> ถ้าไม่มีจุดอ้างอิงเวลา ผู้เรียนแต่ละคนจะหยุดคนละที่
> และจะสรุปผลไม่ได้ว่าใครทำถูก

## 6. Waveform Editor

Waveform Editor ใช้ป้อน pattern ลงในสัญญาณแบบกราฟิก
เหมาะกับรูปแบบที่พิมพ์คำสั่งยาก เช่น สัญญาณนาฬิกาที่มี duty cycle ไม่ 50%
หรือ pattern ที่ต้องทำซ้ำหลายรอบ

เปิดจากเมนู **Tools → Waveform Editor**

วิธีใช้

1. เลือกสัญญาณที่ต้องการป้อน
2. กำหนดค่าเริ่มต้นและช่วงเวลาที่แต่ละค่าคงอยู่
3. บันทึกลงไฟล์ `.wlf`
4. โหลดกลับเข้ามาด้วย `vsim` หรือคำสั่ง `load`

วิธีนี้เหมาะกับการสร้าง stimulus ที่ใช้ซ้ำหลายครั้ง
แต่ไม่เหมาะกับ testbench ที่ต้องส่งมอบ เพราะผลลัพธ์ขึ้นกับไฟล์ภายนอก

## แบบฝึกหัดท้ายบท

1. รัน `ex02_force_release` แล้วทำตามขั้นตอนในหัวข้อ 5.2
   จดค่าของ `cnt` ก่อนและหลัง `force`

   อธิบายว่าเพราะอะไรจึงไม่มีผล

4. ลอง `force` แล้วไม่ `release` แล้วรันต่อ สังเกตว่าเกิดอะไรขึ้น
5. เปิดหน้าต่าง Drivers ของ `tb_counter_forced/en` แล้วบันทึกผล

1. `force` `deposit` และ `apply` ต่างกันอย่างไร
