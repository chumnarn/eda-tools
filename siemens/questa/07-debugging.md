## 1. ลำดับการ debug ที่ได้ผล

> อย่าเริ่มจากการกด step ทีละบรรทัดทันที
> เพราะจะใช้เวลานานและมักไปทางผิด

ลำดับที่ให้ผลกว่า

1. **อ่านอาการให้ชัด** — error เกิดเมื่อไร ค่าผิดเป็นอะไร คาดว่าจะได้อะไร
2. **หาขอบเขตให้แคบ** — ใช้ waveform หาเวลาที่เริ่มผิด แล้วไลย้อนกลับ
3. **ตั้ง breakpoint ที่จุดที่ผิด** ไม่ใช่ที่จุดที่อาการปรากฏ
4. **ดูค่าที่จุดนั้น** — ค่าต่างจากที่คาดหรือไม่ ถ้าตรง แปลว่าปัญหาอยู่ที่อื่น
5. **เดินย้อนกลับ** ทีละจุดจนกว่าจะพบจุดที่ค่าเริ่มผิด

ข้อ 4 คือหัวใจ — ถ้าค่าที่จุดที่ตั้ง breakpoint ถูกต้องอยู่แล้ว
การ step ต่อจะไม่ช่วยอะไรเลย ต้องย้อนกลับไปตั้ง breakpoint ที่จุดก่อนหน้า

## 2. เตรียมการ debug ด้วย testbench ที่ตรวจผลได้

### 2.1 ทำไมต้องมี golden model

ถ้า testbench เป็นแค่ชุด stimulus ที่ไม่ตรวจผล
ผู้เรียนจะต้องนั่งดู waveform แล้วเทียบด้วยตา ซึ่งช้าและพลาดง่าย

testbench ที่ตรวจผลได้จะบอกได้ทันทีว่า

- ผลผิดตรงจุดไหน
- ผิดไปเท่าไร
- เกิดกี่ครั้ง

ตัวอย่างจากชุดตัวอย่าง

```vhdl
if to_integer(unsigned(cnt)) /= exp_v then
  error_count := error_count + 1;
  report "cnt mismatch: got " & integer'image(to_integer(unsigned(cnt)))
         & " expected " & integer'image(exp_v)
         severity error;
end if;
```

ข้อความนี้บอกทั้งว่าผิดตรงไหนและผิดไปเท่าไร โดยไม่ต้องเปิด waveform

### 2.2 ใช้ severity ให้เหมาะกับจุดที่ต้องการ

| severity | ใช้เมื่อ |
|---|---|
| `note` | บันทึกข้อมูล เช่น ค่าที่ได้รับ — ไม่หยุด simulation |
| `warning` | สิ่งที่น่าสงสัยแต่ยังไม่ผิด |
| `error` | ผลไม่ตรงคาด — สะสม error แล้วทำงานต่อ |
| `failure` | ปัญหาร้ายแรง หยุดเลย เช่น timeout |

รายละเอียดเพิ่มเติมอยู่ใน[บทที่ 9](09-assertions-and-severity.md)

## 3. การตั้ง breakpoint

### 3.1 วิธีตั้ง

1. เปิดไฟล์ในหน้าต่าง Source
2. คลิกในคอลัมน์เลขบรรทัดของบรรทัดที่ต้องการ
3. จุดสีแดงปรากฏแปลว่าตั้งแล้ว

### 3.2 เงื่อนไขที่ต้องรู้

> **ห้ามตั้ง breakpoint บนบรรทัดที่ไม่ใช่คำสั่งที่ทำงานได้**
> เช่น บรรทัด `library ieee;` หรือบรรทัดว่าง

Questa SIM Tutorial ระบุว่าเลขบรรทัดที่ตั้ง breakpoint ได้จะแสดงเป็นสีแดง

### 3.3 ตั้งจากบรรทัดคำสั่ง

```text
break tb_counter_tut.vhd:78
```

รูปแบบคือ `break <ชื่อไฟล์>:<เลขบรรทัด>`

### 3.4 ตั้งแบบมีเงื่อนไข

```text
break tb_counter_tut.vhd:78 if cnt = 16#FF#
```

มีประโยชน์มากเมื่อ testbench ทำงานหลายรอบ
แทนที่จะหยุดทุกรอบแล้วค่อยไล่หา

### 3.5 จัดการกับ breakpoint

| คำสั่ง | ผล |
|---|---|
| `break` | แสดงรายการ breakpoint ทั้งหมด |
| `break -delete` | ลบทั้งหมด |
| `break -disable <เลข>` | ปิดใช้งานชั่วคราว |
| `break -enable <เลข>` | เปิดใช้งานอีกครั้ง |

### 3.6 เลขบรรทัดของ VHDL ต้องตรวจสอบเสมอ

> เลขบรรทัดของ VHDL และ Verilog ที่เป็นวงจรเดียวกัน **ต่างกัน**
> เพราะ VHDL มีบรรทัด `entity` `architecture` `begin` ที่ Verilog ไม่มี
> ตัวอย่างใน Questa SIM Tutorial คือ Verilog `counter.v` ตั้ง breakpoint ที่บรรทัด 36
> แต่ VHDL `counter.vhd` ต้องตั้งที่บรรทัด 39

ให้เปิดไฟล์ดูเสมอก่อนตั้ง ไม่ใช่อ้างเลขจากที่อื่น

## 4. คำสั่ง step

| คำสั่ง | ผล |
|---|---|
| `step` | ทำขั้นตอนถัดไปใน process ปัจจุบัน ถ้าเข้า procedure ให้เข้าไปด้วย |
| `step -over` | ทำขั้นตอนถัดไปโดยไม่เข้า procedure ที่ถูกเรียก |
| `next` | ทำขั้นตอนถัดไปในระดับเดียวกับ process ปัจจุบัน |
| `run` | ทำงานต่อจนถึง breakpoint ถัดไปหรือจนจบ |
| `finish` | จบการจำลอง |
| `resume` | ทำงานต่อโดยไม่หยุดที่ breakpoint อีก |

ในหน้าต่าง GUI มีปุ่ม **Step Into**, **Step Over** และ **Step Out**
บนแถบเครื่องมือ Step

> **คำแนะนำ:** อย่า step ทีละบรรทัดในวงจรลำดับ
> เพราะจะเสียเวลามากโดยไม่ได้ข้อมูลที่จำเป็น
> ให้ตั้ง breakpoint ที่ขอบนาฬิกาหรือที่จุดที่สงสัยแทน

## 5. การดูค่าของตัวแปร

### 5.1 คำสั่ง `examine`

```text
examine cnt
examine -radix hex tb_counter_tut/cnt
examine -time tb_counter_tut/cnt
```

ตัวเลือกที่ใช้บ่อย

| ตัวเลือก | ความหมาย |
|---|---|
| `-radix <ฐาน>` | ฐานที่ใช้แสดงผล |
| `-time` | แสดงค่าพร้อมเวลาที่เปลี่ยนแปลง |
| `-hierarchical` | แสดงค่าของวัตถุทั้งหมดใน hierarchy |
| `-lines` | แสดงค่าพร้อมเลขบรรทัดที่เปลี่ยน |

### 5.2 คำสั่ง `watch`

```text
watch tb_counter_tut/cnt
```

ทุกครั้งที่ค่าเปลี่ยน คำสั่งจะพิมพ์ค่าใหม่ออกมาอัตโนมัติ
เหมาะกับการติดตามสัญญาณที่เปลี่ยนไปเรื่อย ๆ

### 5.3 ดูจากหน้าต่าง GUI

| วิธี | ผล |
|---|---|
| หน้าต่าง Objects | แสดงค่าปัจจุบันของสัญญาณที่เลือก |
| วางเมาส์เหนือตัวแปรในหน้าต่าง Source | แสดงกล่องสีเหลืองพร้อมชื่อและค่า ณ เวลาของ cursor ในหน้าต่าง Wave |
| คลิกขวาที่ตัวแปรในหน้าต่าง Source แล้วเลือก **Examine** | เปิดหน้าต่าง Source Examine พร้อมค่า |

> วิธีที่สะดวกที่สุดสำหรับ VHDL คือการวางเมาส์เหนือตัวแปรในหน้าต่าง Source
> เพราะได้ทั้งค่า ณ เวลาของ cursor และตำแหน่งในโค้ดพร้อมกัน

## 6. Delta cycle — สาเหตุที่ค่าไม่ตรงคาด

### 6.1 VHDL มี delta cycle แต่ Verilog ไม่มี

เมื่อสัญญาณหนึ่งเปลี่ยน สัญญาณอื่นที่อ่านจากมันจะอัปเดตในรอบถัดไป
ของ **delta cycle** ซึ่งเป็นเวลาจำลองที่เป็นศูนย์

> นี่คือเหตุผลที่ต้องเขียน `wait for 1 ns;` หลังเปลี่ยนอินพุตของโมดูลแบบ combinational
> ก่อนอ่านค่าเอาต์พุต มิฉะนั้นจะอ่านได้ค่าเก่าเสมอ

ตัวอย่างจากชุดตัวอย่าง `ex03_assert_severity`

```vhdl
din_a <= "00000001";
din_b <= "00000010";
wait for 1 ns;                    -- รอให้ delta cycle จบ
-- ตอนนี้ dout_sum จึงเป็น 3
```

### 6.2 อาการที่พบบ่อย

| อาการ | สาเหตุ |
|---|---|
| ค่าเอาต์พุตเป็นค่าเก่าเสมอ | ไม่ได้รอ delta cycle ก่อนอ่านค่า |
| ค่าเปลี่ยนไปหนึ่งรอบนาฬิกาแต่ไม่ตรงที่คาด | อ่านค่าสัญญาณที่ถูก assign ด้วย `<=` ใน clocked process ซึ่งให้ค่าเก่า |
| ค่าเป็น `U` หรือ `X` | สัญญาณยังไม่มี driver หรือถูกขับพร้อมกันสองที่ |
| simulation ไม่จบและเวลาไม่เดิน | มี process ที่ไม่มี `wait` วนวนไม่รู้จบ |

### 6.3 กฎการอ่านค่าใน testbench

| ชนิด DUT | ต้องรออะไรก่อนอ่านค่า |
|---|---|
| combinational | `wait for 1 ns;` |
| synchronous (ขอบนาฬิกาขึ้น) | `wait until rising_edge(clk); wait for 1 ns;` |
| asynchronous (ขอบนาฬิกาลง) | `wait until falling_edge(clk); wait for 1 ns;` |

## 7. ตัวอย่างการ debug จริง

### 7.1 อาการ

ตัวอย่าง `ex02_force_release` รายงานว่า

```text
cnt mismatch: got 5 expected 4
```

### 7.2 วิเคราะห์จากข้อความ

1. ค่าที่ได้คือ 5 ค่าที่คาดคือ 4 ต่างกัน 1
2. ค่า 4 คือค่าที่ค้างไว้ตอน `en` ถูกปิด
3. ตัวนับนับไปหนึ่งครั้งแม้ `en` เป็น 0 → มีอะไรมาขับ `en` เป็น 1

### 7.3 ตรวจสอบ

ดู waveform ของ `en` ในช่วง 46–76 ns
พบว่า `en` เป็น 1 ทั้งช่วงที่ testbench ควรจะขับเป็น 0

### 7.4 ไปที่ prompt แล้วตรวจ

```text
examine tb_counter_forced/en
```

ถ้าเห็นค่าเป็น 1 ทั้งที่ testbench ขับเป็น 0
แปลว่ามีการ force ค้างอยู่ หรือมี driver อื่น

### 7.5 ตรวจ driver

ในหน้าต่าง Structure (sim) คลิกขวาที่สัญญาณ `en` แล้วเลือก
**Drivers** จะเห็นว่ามีใครขับสัญญาณนี้อยู่บ้าง

### 7.6 แก้และยืนยัน

```text
release tb_counter_forced/en
run -all
```

ถ้าข้อความ mismatch หายไป แปลว่าสาเหตุคือการ force ที่ค้างอยู่จริง

> บทนี้เป็นการอธิบายวิธีวิเคราะห์
> ตัวอย่างจริงที่ทำให้เกิดอาการนี้คือการ force `en` ใน
> [ex02_force_release](../../../code/reference/questa/examples/ex02_force_release/README.md)

## แบบฝึกหัดท้ายบท

1. จงแก้โค้ด `ex00_counter_tutorial` ให้นับผิด แล้วใช้วิธีในบทนี้หาสาเหตุ
   โดยไม่ใช้ waveform ดูก่อน แล้วค่อยเปรียบเทียบกับ waveform
2. ตั้ง breakpoint พร้อมเงื่อนไขที่ `ex00_counter_tutorial`
   ให้หยุดเฉพาะตอนที่ `cnt` เท่ากับ 4
3. ใส่ `wait for 1 ns;` ผิดตำแหน่งใน testbench แล้วอธิบายว่า
   ค่าที่อ่านได้จะผิดอย่างไร
4. ใช้ `watch` ติดตามค่า `cnt` ตลอดการจำลอง แล้วเทียบกับผลที่ได้จาก `examine`
5. เปิดหน้าต่าง Drivers ของสัญญาณ `en` ใน `ex02_force_release`
   แล้วบันทึกว่ามี driver กี่ตัว

## คำถามท้ายบท

1. ลำดับการ debug ที่ได้ผลคืออะไร และเหตุใดข้อ "ดูค่าที่จุดที่ตั้ง breakpoint" จึงสำคัญ
2. ทำไมห้ามตั้ง breakpoint บนบรรทัดที่ไม่ใช่คำสั่งที่ทำงานได้
3. delta cycle ของ VHDL ทำให้เกิดอาการอะไร และแก้อย่างไร
4. `step` กับ `next` ต่างกันอย่างไร
5. ทำไมการตรวจสัญญาณที่มี driver หลายตัวต้องใช้หน้าต่าง Drivers
